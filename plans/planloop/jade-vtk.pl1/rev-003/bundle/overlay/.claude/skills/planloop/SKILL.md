# planloop

A **policy overlay on `claudex-loop`**: every review is one `runner.py review` call, launched through `scripts/planloop.py dispatch` so that it is bound to a frozen input bundle and verified afterwards. The skill decides who plans, which effort Codex gets, what a review is bound to, when a plan escalates and when the plan counts as approved. It cannot guarantee every defect is found: a passed gate means the defects this process looks for were looked for, by an independent reviewer, on exactly these inputs.

History: established 2026-09-22; Opus default planner 2026-09-23; medium floor and fresh high gate 2026-10-21 (`quartz-rs-nve`, after e0n). **Revised 2026-10-22 (Mike, `quartz-rs-lur`)**: the 12-call cap and reserved rounds are gone; receipts are verified from runner and Codex records instead of host-written fields; inputs are frozen; finding state moved into Beads; approval became a readiness check. **2026-11-02 (Mike, `quartz-rs-eps`/`5l6`)**: one planner contract (`references/handback.md`) with a read-only `handback --check`; on the escalated track Fable drafts and redesigns, Opus writes FIX revisions. **2026-11-04 (Mike, cgr.pl1)**: Opus also writes FIX answers to HIGH findings (Fable only for the first draft and redesigns); every run's reviewer and gate models are pinned (Astra for both by default) and can differ per run. **2026-11-05 (Mike, cgr.pl1)**: a plan too large for one message may be handed back as the planner's checked scratch file, bound by the sha256 its final message names (`handback --draft`). **2026-11-08 (Mike, `quartz-rs-72m`)**: size policy and shrink meaning check (see "Plan size and shrink-only revisions").

**Adopted for JADE (2026-11-14).** This skill was built for quartz-rs; the history above and the `quartz-rs-*`, `cgr`, `rao`, `jkj`, `dsk` ids it cites are that project's provenance and are not beads in this repository. The mechanics are unchanged. What is JADE's: five more risk domains (`consent-gate`, `privacy`, `authorization`, `secrets`, `schema-migration`) and the JADE triggers under "Risk classification"; discovery over this repo's layout (`docs/handoff/`, `docs/adr/`, the phase files, `docs/handoff/beads/id-map.json`); the JADE rubric items; and the rule that nothing sent to Codex carries pilot data or secrets ("Evidence"). **Reviewer backends (Mike, 2026-11-14).** A run reviews with one of two backends, recorded in `run.json`: `claude` (the JADE default for a new run: every round and the final gate are a fresh, read-only Claude Opus `Plan` agent at high effort, and approval also needs Mike's sign-off file) or `codex` (everything in this skill that names Codex, unchanged). Codex is used only when Mike says so for a run (`init --reviewer-backend codex`, or `backend` on an existing run). A `run.json` with no backend field, written before this change, is `codex`. Where this skill says "Codex" for a review round, read "the run's reviewer"; the Codex-specific checks (runner invocation, rollout, systemd scope, accepted Codex versions) apply only to `codex` calls.

Binding project sources: `CLAUDE.md` (the non-negotiable rules 1 to 8), `docs/handoff/ARCHITECTURE.md`, `DECISIONS.md` (and `docs/adr/` once Phase 0 commits it), `DATA-MODEL.md`, `EVENTS.md`, `PRIVACY.md`.

## Stop conditions (the only ones)

Keep revising and reviewing until the gate approves. Token cost and the number of rounds are never reasons to stop or to weaken a review. Stop only for:

1. an explicit stop from Mike;
2. a genuinely missing authorization or decision (scope, a requirement conflict, risk acceptance, a disagreement the evidence cannot settle) → `state --set needs_decision`, ask Mike;
3. an infrastructure or evidence blocker that prevents progress → `state --set blocked` (the tool sets it itself, and `dispatch` refuses, after three invalid review attempts in a row, across calls). Do not retry an unchanged blocker: nothing is dispatched until `state --set active --reason "<what changed>"` records the change, which also restarts the count.

Never manufacture approval to escape a disagreement. Repeated findings trigger escalation, structural redesign or more evidence, followed by more review (see Recurrence).

| Property | How | Kind |
|---|---|---|
| Requested model/effort | `command.json` argv and `result.json` must agree with the dispatch record | mechanical |
| Effective model/effort/sandbox | Codex CLI's own rollout `turn_context` (`~/.codex/sessions`); must equal the request | mechanical, see Limits |
| Fresh context | no `resume` in argv, `previous` null, prompt is the rollout's first and only user turn, no lineage fields, session id unused in the run. The one exception (Mike, 2026-10-24): Codex's own pre-prompt context turn, accepted only when every item in it is exactly the `# AGENTS.md instructions for <the call's cwd>` wrapper around the frozen snapshot's AGENTS.md, or an `<environment_context>` naming that cwd; anything else in it is an earlier turn | mechanical |

| Finding resolution | Beads state must reference a counted receipt with `finding R<k>: resolved` (later call than the raise) or a Mike decision file | mechanical |

| *claude backend:* read-only, isolated to the copy | no Edit/Write/NotebookEdit/MultiEdit call; only Read, Grep, Glob, Bash (and the handback); every Bash command starts `cd <copy> && ` or `cd <copy>/<subdir> && ` (target absolute, no `..`, lexically inside the copy; quoted forms allowed) and is checked with the Codex isolation check (`forbidden_patterns`, `climbs_out`) and for writes (redirection into a file, rm/mv/cp/mkdir/touch/tee/ln/chmod, `sed -i`, writing git subcommands (a list-only `git branch` is allowed), bd, planloop.py); every `file_path`/`path` input is an absolute path inside the copy, Grep/Glob need a `path` | detected, **not prevented**; writes by an interpreter's inline code are not detected |

## Effort and models

| Stage | Model | Effort |
|---|---|---|
| Plan / revise, ordinary | Opus (`Plan` subagent) | medium |
| Plan, escalated: revision 1 (or, for a run escalated later, its first escalated revision, `planloop_escalated_revision`), any revision while `planloop_redesign_required` is set or answering an open or reopened finding with `REDESIGN` (answer lines carried over for closed or fix-proposed findings do not count) | Fable (`Plan` subagent, `model: "fable"`) | high |
| Revise, escalated: every other revision, including FIX answers to HIGH findings | Opus (`Plan` subagent, `effort: "high"`; Mike, 2026-11-02, HIGH answers 2026-11-04) | high |
| Working, focused or adjudication round | Codex, the run's reviewer model | medium floor; high on the escalated track and after any reopen or redesign |
| Final gate | Codex, fresh session, the run's gate model (the reviewer model when none is set) | high |
| Triage (mechanical checks only) | Codex | low; never counts as review or verification |
| Every round and the final gate, **claude backend** (JADE default) | a fresh background `Plan` agent, `model: "opus"`, never resumed | high, always (`dispatch` refuses any other effort and has no triage) |

`handback` enforces the escalated rows: it accepts `fable` always and `opus` only when none of the Fable conditions holds, names the condition when it refuses, and refuses any track other than `ordinary`/`escalated`. Runs escalated before 2026-11-02 have no `planloop_escalated_revision` and count as escalated from revision 1. It also refuses while a Beads intent is unfinished, so the policy is judged on settled state. `publish` refuses the first escalated revision unless its handback came from Fable or Mike's override (an Opus revision staged before the escalation must be re-planned). Mike's per-run override (`planloop.py planner --run R --model opus --quote "<his words>"`, first used on dsk.pl1, 2026-10-26) still lets Opus write any revision. The handback record's `completion.planner_basis` says what accepted the model: `fable`, `opus-fix-revision` or `override` (with his words copied in).

**Planner agents.** A fresh `Plan` agent per revision by default. Resume a planner only for a pure resubmission after a refused handback, and never resume one past about 300k `subagent_tokens` (a resumed agent's usage grows every revision). Record per revision, in the run bead's notes: planner model, revision kind (initial/FIX/REDESIGN/HIGH), fresh or resumed, `subagent_tokens`, and whether the fix resolved on first review. Don't combine a size cut with a fix; do the shrink as its own shrink-only revision (defined under "Plan size and shrink-only revisions"). A revision that answers findings and is more than 5% smaller than its predecessor (even when only its change log shrank) gets a `WARN` at `--check`, `handback` and `publish`, and its reviewer is asked to check that every cut is explained; a revision published by older planloop code without `cut` records no answers, so it never gets this warning.

**Reviewer backend.** `init --reviewer-backend claude|codex` (default `claude` for a new run; a re-run of `init` keeps the run's backend). `planloop.py backend --run R --set claude|codex --quote "<Mike's words>"` switches an existing run from the next dispatch, recording his words, the previous backend and the last call number in `run.json` `backend_changes`; a gate from before the switch never counts. The Codex model settings below stay in `run.json` and apply whenever the run is on `codex`.

**Codex models.** `run.json` names the model for working, focused and adjudication rounds (`reviewer_model`) and for the final gate (`gate_model`); `init` pins `gpt-6-astra` for both unless told otherwise (`null` would follow Codex's configured default, which can change under a run). Override with `init --reviewer-model M --gate-model G`, or on an existing run with `planloop.py reviewers --run R --model M --gate-model G --quote "<Mike's words>"`, which records his words and the previous models in `run.json` and applies from the next dispatch. Every receipt checks the model Codex actually ran against the one its dispatch requested. (Mike, 2026-11-04: Astra for every review by default; he says when to move working rounds to `gpt-6-sol`, when usage is low, with `reviewers`.)

Effort only rises within a run (the run bead's `planloop_min_effort`). `xhigh`/`max` are always refused; allowing them is Mike's decision and would be a change to this skill. Every call is a fresh session: the snapshot path changes per revision, so resume is never used.

## The tool

`scripts/planloop.py` (stdlib Python; run from the repository; file formats in `references/formats.md`, the planner contract in `references/handback.md`). Run directory: `plans/planloop/<run>/` (`<run>` = `<bead>.pl<N>`). State outside the checkout: `~/.local/state/planloop/<run>/` (snapshots, runner artifacts, Codex rollout copies; never committed). Exit codes: 0 ok, 1 check failed, 2 unverifiable, 3 conflict. Bad input never produces a traceback: specific checks remain where they give better advice, and any other malformed record stops the command with one `FAIL  <command>: a record it read is malformed (...)` line (exit 1); set `PLANLOOP_DEBUG=1` to see the traceback of that generic case.

```
planloop.py init --run <bead>.pl1 --bead <bead> --track ordinary|escalated --risk-domains <list|none> --rationale "<why>" [--reviewer-backend claude|codex] [--reviewer-model M --gate-model G]
planloop.py reviewers --run R --model M --gate-model G --quote "<Mike's words>"
planloop.py backend  --run R --set claude|codex --quote "<Mike's words>"   # from the next dispatch
planloop.py handback --run R --revision N --nonce X --transcript <agent>.jsonl [--draft <nonce-named file>]
planloop.py handback --run R --check [--revision N] < draft   # read-only content check; planners run it too
planloop.py bundle   --run R --revision N --nonce X --inputs inputs.json
planloop.py publish  --run R --revision N --nonce X        # then: findings propose --run R
planloop.py dispatch --run R --call C --attempt A --kind working|focused|adjudication|gate|triage --effort E
planloop.py receipt  --run R --call C --attempt A --transcript <agent>.jsonl|none   # claude backend, after the agent finished
planloop.py signoff  --run R --quote "<Mike's words>"   # claude backend: writes decisions/A<n>.json for the counted gate
planloop.py findings ingest --run R --call C --attempt A --map map.json
planloop.py findings decide --run R --decision plans/planloop/R/decisions/Dn.json
planloop.py findings check --run R
planloop.py gate --run R --publish          # then plain `gate --run R` (or check_receipt.sh --run R) re-verifies
planloop.py ledger --run R                   # regenerates the read-only projection
```

Chaining steps: never write `cmd | tail && next` — `tail` exits 0, so a refused handback lets bundle/publish/propose run anyway. Use `set -o pipefail` and `cmd | tail || exit 1` per step, run the chain in the background (`bundle` takes over 120 s), and never report a step as passed before reading its output.

## Risk classification (before revision 1, required)

Classify the work before the first planning call and record it with `init`. The domains are `recovery`, `reconciliation`, `persistence` (persistence guarantees), `ordering`, `idempotency`, `session-identity`, `state-machine`, `cross-system-consistency`, `silent-corruption` and `concurrency` (difficult concurrent behaviour), plus JADE's:

| Domain | JADE work that touches it (non-exhaustive) |
|---|---|
| `consent-gate` | anything on the `class_kits.logging_enabled` path: ingest (`p6-ingest`), server progress (`p5-progress`), live stuck alerts held in memory (`p7-live-stuck`), quiz/exit-card/note acceptance, the client's stop-queueing rule, and the `p6-nolog-invariant` test itself (CLAUDE.md rule 2) |
| `privacy` | what is stored or logged about children or adults: event and table shapes, logs and Caddy config (no IPs, codes, tokens, bodies), exports, deletion (`p9-delete`), retention (`p9-retention`), the privacy doc and consent appendix (rules 1 and 4) |
| `authorization` | route groups `(student)`/`(adult)`/`(staff)`/`api`, the authorization matrix, identity taken from the session and never the body (rule 3), signed media URLs, entitlements, 404-not-403 |
| `secrets` | kit-code generation, normalisation and HMAC with `CODE_PEPPER`, join codes, session/device/invite tokens (stored hashed), argon2id, rate limits and lockouts that protect them, config/secret handling |
| `schema-migration` | any migration: forward-only, compatible with the previous app version (health-gated rollback), the events table's append-only grants, `delete_kit_data`, `content_steps` registry sync |

Event ingest is also `idempotency` and `ordering` (UUIDv7, `client_ts` clamping, `seq` gaps, offline replay); device sessions and join codes are `session-identity`; code redemption is `concurrency` and `state-machine`; content version locking (`content.lock.json`, permanent step ids, rule 6) is `silent-corruption`, because an un-bumped edit silently breaks version comparisons. If the work touches any of them, or you are unsure whether it does, it starts on the **escalated track**: `--track escalated --risk-domains <the ones that apply>`, Fable drafts revision 1 at high effort (Opus may write later FIX revisions, see Effort and models) and every Codex round runs at high. Otherwise `--track ordinary --risk-domains none`. Either way `--rationale` says why, in a sentence that names what the work changes. Fundamental architecture, an unresolved Opus/Codex disagreement, repeated failed attempts, or a sign that the architecture itself may be wrong also justify starting escalated. No finding is needed to choose the escalated track.

Two JADE stops come before any classification: a plan that would change or relax one of CLAUDE.md's rules 1 to 6 (and not merely implement them) is `needs_decision` for Mike before revision 1; a plan that would deviate from an accepted decision (`DECISIONS.md` / `docs/adr/`) is a `decision` bead labelled `human`, and the run stops (rule 8). Never plan around either. A bead labelled `human` is never planned for implementation.

`init` records the classification in the run bead's metadata (`planloop_risk_domains`, `planloop_risk_rationale`, `planloop_track`, `planloop_min_effort`, `planloop_escalated_revision`), refuses `--track ordinary` with any domain listed, and never lowers a track: re-running it can only escalate, updating the domains and rationale. Escalation is preserved for the rest of the run, including every later review round and the gate.

## Step 0: requirement discovery (before revision 1; again before the gate)

1. Seed: `bd show <bead>`, `bd dep list <bead>`, `bd dep list <bead> --direction=up`, `bd search <bead>`. Look up the bead's plan key (`p6-ingest` and the like) in `docs/handoff/beads/id-map.json`; its section in `docs/handoff/phases/phase-NN-*.md` and its acceptance criteria are binding sources. So are the parts of `CLAUDE.md`, `ARCHITECTURE.md`, `DECISIONS.md`/`docs/adr/`, `DATA-MODEL.md`, `EVENTS.md` and `PRIVACY.md` the work touches.
2. `command grep -rln` in `plans/`, `docs/` (handoff, adr, runbook, `threat-model.md`, generated `events.md`, `content-format.md`), `migrations/`, `src/lib/shared/events/` and `tests/` for the bead id, its plan key and every table, column, event type, route, config variable and content field the work touches (plain `grep` in this shell is a ugrep wrapper that skips directories without `-r`; the only `rg` on PATH is the Windows Codex app's). Prove a search can match before trusting an empty result.
3. Transitive closure: for every file found, follow the plans and beads it references, with a visited set and no hop limit. If the set is too large to read, split it and say so.
4. Classify each source `binding` / `candidate` / `irrelevant`. Write them all to the discovery record. A binding source needs an obligation row (`OB<n>`, exact text); a candidate must be supplied to the reviewer (`repo_files`). Anything you know you did not cover goes in `known_omissions`, which blocks the bundle: fix the omission instead.

Hashing proves the frozen inputs did not change; it does not prove you found every relevant source. That part is your obligation and is recorded, not enforced.

## Planning and the handback

Run the `Plan` subagent **in the background** so its transcript is persisted, with a fresh nonce per request (`python3 -c "import secrets;print(secrets.token_hex(8))"`). It has no Write/Edit and must not write files, except one self-check scratch file named with the nonce under `${TMPDIR:-/tmp}`, for drafts too large for a heredoc (`references/handback.md`), deleted after the check and never the handback. The planner prompt gives the run id, revision, nonce, findings and brief, and **points at `references/handback.md`** (the one planner contract: markers, title, change log `FIX`/`REDESIGN`/`REJECT`/`REMOVED`/`SHRINK`, what a lost line is, RR lines, inventory, byte-exact obligations) instead of restating any rule. Tell the planner to self-check with `planloop.py handback --run R --check` before handing back (Plan agents have Bash: pipe the draft through a heredoc on stdin; over about 100 KB a heredoc exceeds the 128 KiB argument limit, so the contract's chunked scratch file is used). Never show format by example in the prompt; an example's wording gets copied (rao rev 26 put "(unchanged from rev 25)" on every inventory line).

`handback` takes the bytes from the transcript's `SubagentHandback` (or final `end_turn` message), requires the agent's `finished` flag and the delivery acknowledgement, checks the planner model (above), and applies every content rule of the contract; `handback --check` runs the same content checks, shared code, without a transcript, and writes nothing. A transcript whose ids, handback input or final message are not the shape Claude writes is `UNVERIFIABLE` (`transcript format not recognised: ...`); a write error or SIGINT while staging removes what it created (`could not stage revision N in <staging> (<error>); nothing was staged`, exit 2, or `INTERRUPTED`, exit 130), so the same handback can be run again; a handback that finds its staging directory created by another handback with the same nonce while it ran stages nothing and says so (`<staging> already exists: another handback with this nonce staged it, or is staging it, while this one ran; ...`, exit 1); a staging directory without `handback.json` (a handback killed while staging) is never removed automatically, since a handback staging it now looks the same: the next handback with that nonce says so (`<staging> already exists, without handback.json: ...`) and it is removed by hand. On refusal, send the planner the printed reasons verbatim (a `--check` of its text lists the exact lost lines) and ask for a corrected complete plan. There is no host acknowledgement path: every removal is explained in the plan itself and listed to the reviewer, who judges it.

Matching bytes prove faithful transfer, not completeness. Before bundling, read the change log against the diff from the previous revision and send back anything important that vanished, even if the checks pass.

**Close a finding class, not an instance.** After the second single-line doc or wording finding of the same class in a run, run the class's predicate yourself (a `command grep -rn` sweep of the plan and docs for the class) before the next round, put the hits in the brief, and have the planner close the whole class in one revision (on rao.pl1 this ended a tail of one-line findings in two rounds).

**Answers to recovery/ordering findings must close the general interleaving**, not only the instance the reviewer traced. Before publishing a revision, ask whether the fix still holds for every interleaving. For JADE that means: a batch retried, duplicated or delivered out of order; a batch queued offline across a logging toggle (logging switched off or on while events sit in the device queue); a facilitator closing or rotating the join code mid-join; a kit's devices reset while a batch is in flight; and two adults redeeming the same code at once. (On quartz-rs one finding needed three revisions because each answer closed only the named case.)

## Inputs, bundle and publication

Write `inputs.json` (format in references): brief path, `repo_files`, `dir_inventories`, binding `beads` (default fields title, description, acceptance criteria, design; add `notes` only when notes carry the requirement), `obligations` (exact text), evidence records, discovery record. The brief holds the rubric below, the change map (navigation only), predicate results and anything else the reviewer needs.

`plans/planloop/` itself is never a review input: it is excluded from the overlay and every inventory in code, whether or not git ignores it. `bundle` takes its own lock (`.lock-bundle` in the run's state directory, not the run lock, so a long build never holds up dispatch or receipt), so two bundles never build the same staging directory or snapshot at once (the second waits for the first, up to the lock timeout of 30 seconds: if the first still holds the lock then, the second stops `CONFLICT`, exit 3, naming the first; if the first released it in time, the second takes the lock and makes the checks below, so it stops with `staging already has a bundle and revision.json is in place: publish it`, exit 1, when the first built that staging directory); `publish` (not `publish --recover`, which takes only the run lock, after breaking a `.lock-bundle` whose owner is provably dead, and never waits for a bundle) takes the same lock before the run lock (the only command that holds both, so the order cannot invert), so a staging directory is never moved while a bundle is building or finishing it (a `publish` that finds a bundle running waits for it without holding the run lock, up to the lock timeout: if the bundle releases its lock in time, `publish` takes it and goes on, publishing the revision when its bundle is complete; if not, it stops `CONFLICT`, exit 3, with nothing published). A `publish` of a staging directory whose revision is already published stops `CONFLICT`, exit 3: `revision N is already published from another staging (HEAD is revision M); <staging> is a stale staging of it and nothing was published: remove <staging>`, and one with no `revision.json` says `revision N is not bundled: ...` and names the `bundle` to run. `bundle` makes the checks below before it reads the staged handback and again once it holds the lock, so a published, interrupted or missing staging is named as such either way. Once it holds the lock, `bundle` reads the run again and builds only a revision that is not published and whose staging directory is still there, otherwise it stops (exit 1) with nothing touched: `revision N is already published (HEAD is revision M); nothing was changed`, `rev-NNN exists and HEAD is revision M: a publication of revision N was interrupted; ...` (run `publish --recover`), or `<staging> is gone or was never staged (HEAD is revision M); nothing was changed`; a published revision's snapshot is therefore never rebuilt or removed, and a snapshot is removed only by the bundle that created it or, as the leftover of a killed bundle, by the next bundle of that same unpublished staging directory. It builds in a temporary directory (a failed or interrupted build leaves nothing to clean; an I/O error reading or writing any of it, such as a full disk, stops `bundle` unverifiable, exit 2, `could not read or write <path> (<error>); nothing was published: run the command again once that path can be read and written`, with no bundle, `revision.json` or snapshot left behind; a brief that cannot be read is `UNREADABLE`, and when the bundle cannot be removed after its `revision.json` write failed, the message ends `nothing was published: remove <staging>/bundle by hand, then run the command again`, the snapshot removed; when the `revision.json` write reports an error or is interrupted after it landed, the bundle and snapshot are kept and the message ends `revision N's bundle is complete and its revision.json is in place: publish it`, as does a later `bundle` of it, `staging already has a bundle and revision.json is in place: publish it`; a bundle killed outright between moving its bundle into place and writing `revision.json` leaves `<staging>/bundle` alone, and the next `bundle` says to remove it: `staging already has a bundle, but no revision.json: ...`, and that next build removes a `.revision.json.tmp-*` the kill left in the staging directory), freezes everything into the staging directory and builds the snapshot: `git archive` of HEAD, every modified and untracked non-ignored file overlaid, `.planloop-bundle/` with plan, brief, obligations, bead text, evidence and discovery, then made read-only. **What invalidates a review**: a change to a declared repo file, a file added to or removed from an inventoried directory, a change to a binding bead field, a change to an evidence input. **What does not**: commits elsewhere (HEAD moving), bead notes or status, finding beads, ledger regeneration, receipts and other review outputs.

`publish` takes the run lock, checks the staged revision was built on the current HEAD, writes a publishing intent `.publishing-rev-NNN` (the SHA-256 of the `revision.json` it verified), renames the staging directory to `rev-NNN`, replaces the single pointer `HEAD` and, once HEAD reads back, removes the intent (best effort: a removal that fails, for example a drvfs EACCES, prints `NOTE  could not remove .publishing-rev-NNN` and the publication still succeeds; the next recovery retries it, and a directory there gets `remove it by hand` instead). When something other than a regular file (a directory) already sits at that intent path, `publish` stops before writing anything (exit 1, `<path> exists and is not a file; remove it by hand, then publish again`); a failed intent or HEAD write leaves no temporary file behind and stops `publish` unverifiable (exit 2): for the intent `could not write <path> (<error>); nothing was published, HEAD is unchanged`, for HEAD `could not write HEAD (<error>); revision N is in place with its publishing intent`, which the next locking command completes, or moves aside with a NOTE to re-stage it if it no longer verifies (a recovery that cannot write HEAD stops the same way and leaves both in place). Re-running that `publish` (same revision and nonce) once the recovery has completed it prints `revision N (nonce X) is already published (HEAD is revision M); nothing to do` and exits 0; when its staging directory is gone and HEAD has reached N from another staging it fails (exit 1, `already published from another staging`), and when HEAD is below N (the recovery moved it aside) it fails with `<staging> does not exist; revision N is not published` and the advice to re-stage it. A rename that fails with any other I/O error (EIO, not the drvfs EACCES) stops the command unverifiable (exit 2, `could not rename <src> -> <dst> (<error>); the rename did not report success, so it may or may not have taken effect;` then what to do: a drvfs or 9p rename can complete and still report EIO, so the advice holds either way): in `publish` (`run the command again, it re-checks what is on disk`) a staging directory that did not move stays with its intent, so the next recovery drops the intent and `publish` runs again, and one that did move is rolled forward by that recovery, after which `publish` reports it already published; in a recovery's move aside the revision either stays, and the next recovery retries the move, or is already at the named `.orphan-rev-NNN-<hex8>`, and the message carries the `handback` command that re-stages it; when `publish` moves a rejected revision aside the message says `if it is still present the next recovery moves it aside, or publishes it if it then holds exactly the revision publish verified and that revision's cut still holds` (its intent is kept, so that is what recovery decides); in `bundle` a `bundle` directory that appeared has no `revision.json` and must be removed before bundling again; in `dispatch` a reserved call directory that appeared is recorded with `receipt` before the next attempt. A staging directory or published `handback.json` that cannot be read while `publish` checks whether its revision is already published stops it unverifiable with the retry-only advice; nothing is moved. Each operation resolves HEAD once. An interrupted publication is rolled forward or moved aside by `publish --recover` (every locking command recovers first); nothing HEAD references is ever moved. Recovery rolls `rev-NNN` (NNN = HEAD + 1) forward only when it verifies, chains to HEAD, its `cut` holds and `.publishing-rev-NNN` names exactly its `revision.json`, so it never publishes content `publish` did not verify, whatever step a crash or I/O error interrupted; a `rev-NNN` with no intent (a crash leftover of planloop code from before the intent, or a hand-made directory) is moved aside with `no publishing intent names it`, one whose intent cannot be read (not JSON, or not a publishing intent for that revision) with `its publishing intent cannot be read`, and one whose `revision.json` differs from the intent with `it is not the revision publish verified`; all are recoverable by re-staging. A crash after the intent but before the rename leaves the staging directory in place: publish it again. Recovery deletes intents for revisions at or below HEAD, intents with no `rev-NNN` beside them (a crash before the rename, or a revision `publish` moved aside) and the intent of each revision it moves aside, best effort (an intent it cannot delete, or a directory of that name, gets a NOTE and never blocks the command; for a directory the NOTE says to remove it by hand); a newer `publish` of the same revision overwrites an older intent, so a stale intent never blocks it. A recovery that rolls a revision forward prints its size report on stderr; an interrupted publication staged before the size policy (no `cut` in its `handback.json`), or whose `cut` does not hold (below), is moved aside instead (to `.orphan-rev-NNN-<hex8>`), with a NOTE giving the `handback` command that re-stages it; so is any revision above HEAD that does not verify as the one after it (a missing `revision.json`, `plan.md`, `handback.json` or manifest, a plain file named `rev-NNN`, a manifest that is not UTF-8, or something other than a regular file where one of those records should be all count as not verifying; a transient permission error does not: a held-open intent or revision file on drvfs stops the command unverifiable (exit 2, `could not read <path> (<error>); retry once it is no longer held open; if it persists, ` followed by `move <rev-NNN> out of the run directory by hand (it can then be re-staged)` for a file inside the revision being recovered or `move it out of the run directory by hand (a revision is then moved aside and can be re-staged)` for an intent; a file outside that revision, such as the published predecessor's `revision.json` or its snapshot, gets only the retry advice, since moving it would break the chain, and so does an error that names no file, which is reported against `rev-NNN` itself) and moves nothing aside; and a non-file is never moved aside where that would destroy a publication: when it sits in the revision right after HEAD whose publishing intent exists (the publication candidate), or is that intent itself, the command stops with a plain failure (exit 1, `FAIL  <path> is not a regular file (a directory, FIFO, socket, device or dangling symbolic link), so reading it again cannot help; nothing was moved aside or discarded: repair it by hand, or move <rev-NNN> out of the run directory by hand (it can then be re-staged)`, ending `, or move it out of the run directory by hand (a revision is then moved aside and can be re-staged)` for the intent; exit 1 and not 2 because running the command again cannot help) and every locking command stops the same way until it is repaired or moved out; a non-file in any other revision above HEAD, such as a stray `rev-005` whose `revision.json` is a directory, is moved aside like any revision that does not verify), and its NOTE gives that command whenever its `handback.json` still parses as this revision's (otherwise it is moved aside as unreferenced). A Beads read that reports success but returns incomplete findings (for example `[]`) can make a valid `cut` look wrong and move a good revision aside; that is recoverable, since the orphan is kept and the NOTE re-stages it. After renaming the staging directory to `rev-NNN`, `publish` verifies `rev-NNN` again in full (the same deep check as before the rename: every overlay copy, every frozen copy and the snapshot) and compares its `revision.json`, `plan.md`, `handback.json` and `bundle/manifest.json` with the bytes it verified; when that check finds something other than a regular file where a record should be, `publish` moves nothing: it stops with the same `FAIL  <path> is not a regular file (a directory, FIFO, socket, device or dangling symbolic link), so reading it again cannot help; nothing was moved aside or discarded: repair it by hand, or move <rev-NNN> out of the run directory by hand (it can then be re-staged)` (exit 1), HEAD unchanged, leaving `rev-NNN` and its intent for the recovery, which holds it open the same way until it is repaired and then publishes it; when the check fails otherwise (a file that has vanished counts) or the bytes differ, it moves `rev-NNN` aside under the lock before writing HEAD, deletes its now stale intent (best effort) and exits 3 (Conflict), naming the aside directory and what to do next: re-run `publish` with the same nonce when its own staging directory still exists and verifies, otherwise the `handback` command that re-stages it. If the move aside fails (a drvfs EACCES) or the process dies before it, `rev-NNN` stays and the next recovery moves it aside unless it again holds exactly the verified bytes; a read error during that re-check stops `publish` unverifiable (exit 2) with HEAD unchanged, and recovery decides the same way. There are no tombstones (`.rejected-rev-NNN-*`, written by earlier code, are inert and can be deleted). Once `HEAD` is written, a size report that cannot be computed for an ordinary reason (an unreadable receipt, a receipt bound to no authenticated revision, a malformed decision, or any other unexpected error) prints `WARN  size report unavailable: <error type>: <reason>` and the command still succeeds (a recovery still moves the remaining revisions aside); an integrity failure of the chain from HEAD (a record missing inside that authenticated walk counts as one; one that exists but cannot be read is `UNREADABLE` and downgraded like the reasons above) is never downgraded: the command prints that the publication of revision N is complete, then the failure, and exits 2, and a recovery stops there, leaving later revisions in place for the next recovery; the next `dispatch` or `gate` reprints the report and fails as any policy command does. `publish --recover`, every `dispatch` and `gate` print the current policy revision's size and policy lines. Then run `findings propose` to mark the answered findings `fix_proposed`. Install a change to this skill while no planloop command runs, to avoid wasted work (nothing older code does can grant anything; see below).

## Each review round

1. **Evidence**, before the round: check each record the plan relies on still supports its claim; collect only what is absent, invalidated or needs a new observation (rules below). Evidence is collected only against the local development stack (`compose.dev.yml`, the test database harness), the repository and fixtures, never against staging or production without Mike's say-so.
2. `dispatch` (it refuses a blocked run, an effort below the floor, an out-of-order call or attempt). It writes the call's frozen feedback (bundle marker, brief, obligations, dispositions, current Beads finding table, resolution-reporting rules) and launches the runner with `--timeout 1800` against a private copy of the snapshot and an artifact directory of its own (`calls/call-CCC-aA-r-<16 hex digits>` under the run's state directory, named after that copy, `r-<16 hex digits>` in the isolated directory, and created with the reservation: one that already exists is refused, exit 2 with nothing reserved, never reused, so checkouts that share a state directory and a run id never share one), then verifies the call and writes `receipt.json`. Use a background Bash call; it can take half an hour. A runner that cannot be found stops `dispatch` before anything is reserved (exit 2, `claudex-loop runner.py not found ...; no call was reserved and Codex did not run`), and so does a `PLANLOOP_RUNNER` that does not parse as a shell command line (`PLANLOOP_RUNNER does not parse (...); no call was reserved and Codex did not run`) or holds only whitespace (`PLANLOOP_RUNNER holds no command; no call was reserved and Codex did not run`); one that cannot be started (an OSError launching it) prints `NOTE  the review runner could not be started in its scope <U> (<error>); Codex did not run` and the call is recorded `invalid` like a runner that left no artifacts, so the next attempt can be dispatched. If a reservation fails and what it made (its private snapshot copy, its artifact directory) cannot all be removed, the reservation's own error stands and `NOTE  could not remove ...; no review used it, and ...` names what is left and what removes it: before the reservation was renamed to the call directory, its record `.reserve-<uuid>` is kept so that the next dispatch removes it (an OSError then says `no call was reserved and Codex did not run, but its record ... is kept so that the next dispatch removes it`); once it was renamed there, `receipt` of that call removes what is left of the private snapshot copy (it or a leftover `.marking-<name>` of either directory, named by its dispatch.json); an artifact directory still under its own name then holds only its `.planloop-reserve` marker and is removed by hand, as the NOTE says. Only a missing path counts as removed: an error checking whether one is still there keeps the record. When the runner has returned and `receipt` cannot take the run lock (held, or the lock cannot be prepared), `dispatch` keeps the lock's category and error and says `<what ran>; its call.json is written but its receipt is not (<the lock's error>): do not dispatch call C attempt A again (where that says to run the command again, it means `receipt`): record it with `receipt ...``. If `call.json` cannot be written after the runner returned, `dispatch` removes what it wrote and stops unverifiable (exit 2, `could not write .../call.json (...), so the review runner's result is not recorded; record it with `receipt ...` (its call.json is missing (never written, or removed after the failed write), so it is recorded invalid), then dispatch ...`); if even that removal fails it says the attempt is recorded invalid unless `call.json` reads in full, that nothing is recorded while it cannot be read at all, and to carry on from whatever `receipt` prints. `receipt` records a call whose `call.json` does not parse or is not a file, or is missing although the runner left a `result.json`, as `invalid` with that reason, never from the runner's artifacts unless `receipt --artifacts <runner dir>` names them. When the call has neither `call.json` nor a receipt, `<runner dir>` must be the one directory `dispatch` would have recorded: directly in the call's artifact root, and the only `claudex-*` directory there holding a `result.json` file; anything else (a mistyped or relative path, another name, a `result.json` that is not a file, a second candidate) stops `receipt` (exit 1, `--artifacts <dir> is not the one runner directory dispatch would have recorded (...); nothing was recorded: name that directory, or run `receipt ...` without --artifacts, which records the attempt invalid`) and records nothing, so a typo burns no attempt. When it is, `receipt --artifacts` verifies the call with it and only then writes `call.json` naming it (`runner_exit` and `runner_stdout_sha256` null), before the receipt, so every later verification (a plain `receipt` re-run, `gate`) binds the same directory, which must still pass every check, and a verification that stops (unreadable, failed) leaves no `call.json` behind; when the call already has a `call.json` or a receipt, `--artifacts` replaces `call.json` for that one verification only, and every `receipt` command planloop then prints for it carries the same `--artifacts`. If that `call.json` cannot be written nothing is recorded (`could not write .../call.json (...), so <dir> is not bound to call C attempt A and nothing was recorded; run `receipt ... --artifacts <dir>` again once it can be written`, with `, but a partial call.json remains: remove it by hand first` before the `;` when even its removal failed). A runner artifact that is a directory where a file is required (`result.json`, `command.json`, `prompt.txt`, `reply.txt`, `stdout.txt`, `stderr.txt`, `schema.json`, the kept `rollout.jsonl`), or an artifact directory that is not a directory, is recorded `invalid` with an infrastructure reason (`runner artifact <name> is not a file`, `runner result.json: not a file`): re-reading cannot change what the runner left, so the next attempt dispatches. A call's own `feedback.md`, or its revision's `plan.md`, bundle manifest or overlay copies, that is missing or a directory, FIFO or other special file stops `receipt` (and `gate`) with `FAIL  feedback.md: missing or not a file` (`revision N plan.md: ...`, `manifest.json: ...`, `revision N overlay copy of <path>: ...`) and records nothing, and a FIFO is never opened, so it never blocks the command: it is planloop's damaged record, not the review's; repair it, then run `receipt` again. Every other planloop record read as JSON (`dispatch.json`, `running.json`, `receipt.json`, `call.json` aside, `intents/*`, `HEAD`, ...) that exists but is not a regular file stops the command the same way (exit 1, `<record>: not a file (repair it by hand; reading it again cannot help)`), never `UNREADABLE` with retry advice. A reservation that cannot be prepared (a directory that cannot be written, a snapshot that cannot be copied) stops `dispatch` unverifiable: `could not prepare call C attempt A (...); nothing was reserved and Codex did not run: run the command again once the path it names can be read and written`. A `receipt.json` that cannot be written stops `receipt` (or `dispatch`) unverifiable: `could not write .../receipt.json (...), so call C attempt A is not recorded; do not dispatch that attempt again: run `receipt ...` again once it can be written` (with `, but a partial receipt.json remains: remove it by hand first` before the `;` when even its removal failed). A new intent that cannot be written (an I/O error, such as a failed fsync) stops the command unverifiable before any Beads change: `could not write intent <name> (...); no Beads change was made from it: if <path> exists now, the next locking command (`publish --run R --recover`) applies it, otherwise run the command again once it can be written`. An intent whose new state cannot be written after its Beads changes stops the command unverifiable: `could not record intent <name> as applied|verified (...); its Beads changes are made and <name> stays unfinished: once <intents dir> can be written, `publish --run R --recover` replays it to completion`. A planloop record that exists but cannot be read at all (a permission or I/O error, not a missing file) stops the command unverifiable, printed with the prefix `UNREADABLE` (exit 2, `UNREADABLE  <file> could not be read (...); nothing was recorded from it, run the command again once it can be read`). That covers every file planloop reads under the run directory (`run.json`, `HEAD`, `APPROVAL`, `approvals/*`, each `rev-NNN/` file, each call's `dispatch.json`, `feedback.md`, `running.json`, `call.json` and `receipt.json`, `intents/*`, `decisions/*`) and under the state directory (snapshots, private copies, the runner's artifacts and their kept `rollout.jsonl`), Codex's session record and the accepted-versions list, and every directory planloop lists or checks for an entry (the run directory, `reviews/`, a call directory, `intents/`, `decisions/`, a staging directory, the runner's artifact directory, a snapshot, Codex's session store): one that cannot be listed is never read as empty. An overlay copy, or an entry of a snapshot or private copy, whose type cannot be checked (in a directory that can be listed but not searched) or whose link cannot be read is unreadable the same way, and a snapshot or private-copy entry that is neither a regular file nor a symbolic link when it is hashed is `UNREADABLE  <path> could not be read ([Errno 22] not a regular file or symbolic link when hashed); nothing was recorded from it: a FIFO, socket or device never reads as a file, so running the command again cannot help: remove it, or find what put it there, then run the command again`, never hashed as a file (from `dispatch`, once the runner has returned, the advice is to record the call with `receipt` once it is removed). A symbolic link to a directory is hashed as a link (`os.walk` lists it with the directories and never follows it), so adding, removing or retargeting one changes the tree hash. Two keep their own handling: a lock's `owner.json` (never broken automatically, see 6 below) and a revision file or publishing intent for which `publish` or its recovery gives its held-open advice instead (under "Inputs, bundle and publication"). Only a size report after `HEAD` is written downgrades it to its `WARN  size report unavailable`. The error may pass, so the attempt is not recorded invalid for it, and an approved run is not reopened: `state --set active` stops the same way while any record its approval check reads cannot be read. Where something was already done the message says what instead of `nothing was recorded`: once the runner has returned, `dispatch` says `the review runner ran for call C attempt A (exit X); its call.json is written but its receipt is not: do not dispatch call C attempt A again; once it can be read, record it with `receipt --run R --call C --attempt A``; when the runner's artifact directory itself cannot be listed, `the review runner ran for call C attempt A (exit X), but call.json was not written, so its result is not recorded; do not dispatch call C attempt A again: once it can be read, record it with `receipt --run R --call C --attempt A --artifacts <artifact dir>/<the claudex-* directory in it holding result.json>`, or without `--artifacts` if no directory there holds a result.json (it is then recorded invalid)` (for a runner that could not be started, `Codex did not run; once it can be read, record it with `receipt ...``, which records it invalid); once a receipt is written, `call C attempt A is recorded <status> in <path> and stands, but this command stopped before printing it and before checking whether that blocks the run; do not dispatch that attempt again: once it can be read, run `receipt --run R --call C --attempt A` again, which prints it and makes that check` (when what stopped it is a plain failure instead, such as another call's record that is not a regular file, it exits 1 with `<the failure>; call C attempt A is recorded <status> in <path> and stands, but this command stopped before printing it and before checking whether that blocks the run; do not dispatch that attempt again: once that is repaired, run `receipt ...` again, which prints it and makes that check`); and a `gate --publish` that cannot re-read a record after writing its pending approval record says `this approval was not published: the pending record <name> stays unreferenced and APPROVAL is unchanged; once it can be read, run `gate --run R --publish` again`. A `gate --publish` that cannot write its pending approval record stops unverifiable with `could not write <path> (...); this approval was not published: no approval record was written, APPROVAL is unchanged and Beads records no approval candidate for it; once <run dir>/approvals can be written, run `gate --run R --publish` again` (`a partial record <name> remains unreferenced` in place of `no approval record was written` when even its removal failed), and one that cannot write `APPROVAL` with `could not write <run dir>/APPROVAL (...); this approval was not published: the pending record <name> stays unreferenced and APPROVAL is unchanged; once <run dir> can be written, run `gate --run R --publish` again`. Once a receipt is written, a private snapshot copy that cannot be removed (it is first renamed to `.pruned-r-*`, then removed) never fails the command: the receipt is printed as usual and `NOTE  could not remove the private snapshot copy <path> (...); the receipt is recorded and stands and no review needs that copy: remove it by hand (`chmod -R u+w` first) once no planloop process runs` names what is left; running `receipt` again retries a copy the rename did not move. Another call's `dispatch.json` that cannot be read then only skips that call's copy: `NOTE  <file> could not be read (...), so the private snapshot copy of call C attempt A was not checked or removed; the receipt is recorded and stands and no review needs that copy: once it can be read, running `receipt --run R --call C' --attempt A'` again removes the copy` (naming the call just recorded). A round on a shrink-only revision, or on a successor carrying an unjudged one, carries the meaning check ("Plan size and shrink-only revisions"): dispatch it before publishing another revision when it can run; when it cannot (expired observation, changed input, lost snapshot, a text change the inputs force), publish the successor the inputs need, whose rounds carry the shrink's comparison until a counted round judges it.
   **claude backend.** `dispatch --effort high` makes the same checks and the same reservation (call record, frozen feedback, private read-only copy of the snapshot) but starts nothing and needs no systemd scope or runner: it copies the call's feedback into the copy as `.planloop-call/feedback.md`, writes `input/prompt.txt` (short: bundle marker, the plan's and feedback's paths in the copy with their sha256, the read-only and isolation rules, the response schema), prints it between `-----BEGIN PLANLOOP PROMPT-----` and `-----END PLANLOOP PROMPT-----` with the copy's path, and exits 0. Give that text, exactly, to one background `Agent` with `subagent_type: "Plan"`, `model: "opus"`, `effort: "high"`, a fresh context, and never resume it or send it a message. When it has finished, `receipt --run R --call C --attempt A --transcript <its agent-*.jsonl>` (the `.meta.json` beside it is read too) verifies the call as "What is enforced" lists, keeps the transcript, its meta and where they came from in the call's artifact directory (`transcript.jsonl`, `transcript.meta.json`, `transcript-source.json`), and records `backend: "claude"`, the source path and sha256 in the receipt; every later re-verification uses the kept copy. An agent whose meta records no finished run is not recorded (CONFLICT, exit 3: wait for it); one that never ran or will never finish is recorded invalid with `--transcript none`. `receipt` without `--transcript` on an unrecorded claude call records nothing and says so.
3. Read the receipt. `invalid` does not count: fix the cause and retry as attempt 2 or 3 of the same call (a retry may not carry plan changes; a changed plan is a new call). `infrastructure: true` means the call could not be verified, not that the plan is wrong.
4. `findings ingest` with a map from each reviewer finding id to `new`, `new:R<k>` (split/renamed, keeps lineage) or an existing `R<k>`. The map must cover every reviewer finding. Resolution comes only from the reviewer's coverage lines, and only from a review of the revision that carries the fix (a review of an older revision neither verifies nor counts against it). Ingest runs in call order, and `dispatch` refuses while a counted call is not ingested or a published revision has not been through `findings propose`. A later reviewer may withdraw an open finding only with evidence, `finding R<k>: withdrawn: <why its failure scenario cannot occur>`; a bare status is malformed and voids the call. The finding closes as `withdrawn`, but approval also needs the final gate to confirm the withdrawal (see the gate).

A scope is read only through a path proven to be the cgroup tree it was created in, and the proof is made by the command that reads it, where and when it reads: `/sys/fs/cgroup` must be, by `/proc/self/mountinfo`, a cgroup2 mount whose root is the root of this cgroup namespace (the namespace `view` records), and every directory from there to the scope, and each control file, is opened relative to its parent without following a link and must be on that same mount (`mnt_id` in `/proc/self/fdinfo`). `/proc/self/mountinfo` and `/proc/self/fdinfo/<fd>` are read only from a `/proc` whose filesystem type is procfs (`fstatfs`), each on the same device as `/proc`, and a `mnt_id` line that is not one number is an error (`[Errno 18] not procfs: '/proc'`, `[Errno 18] not on procfs: '<path>'`, `[Errno 95] the kernel does not say which mount it is on: '<path>'`). A control file is opened non-blocking and read only when it is a regular file, at most 1 MiB (`[Errno 22] not a regular file: '<path>'`, `[Errno 27] larger than 1048576 bytes: '<path>'`), so a FIFO, a link or an oversized file there is an error and never a hang; `mountinfo` and `fdinfo`, once proven procfs, are read whole, whatever their size (a host with many bind mounts has a `mountinfo` of hundreds of kilobytes). `fstatfs` is called through `ctypes`, loaded only when a scope is read: a Python without `ctypes` runs every other command, and `dispatch` stops at its probe (UNVERIFIABLE, exit 2, `... which this shell cannot see ([Errno 38] fstatfs cannot be called through ctypes (<error>), so it cannot be proven procfs: '/proc')); no call was reserved and Codex did not run`). `cgroup.kill` is opened the same way, for writing and without creating it, so a scope with something mounted over it is never "killed" by writing a file on that other filesystem. A `dispatch` killed before its call was reserved leaves a `reviews/.reserve-*` directory; the next `dispatch` removes every one it finds, with the artifact directory and the private snapshot copy its `dispatch.json` names, each only if it holds the marker that reservation wrote into it (`.planloop-reserve`, holding the reserve directory's name; each directory is made as `.marking-<name>` beside it, marked, and only then renamed to its name, so a directory of that name always holds its marker; a rename that reports an error yet landed is undone at once, since the directory holds this reservation's marker, and the error names the directory, not its `.marking-<name>`; a marked directory is removed by renaming it back to `.marking-<name>` first and only then deleting it, so a removal killed after it deleted the marker leaves a `.marking-<name>` the next `dispatch` removes by name): a directory of that name that was already there, which the killed `dispatch` was about to refuse, holds no such marker and is never touched (marked directories exist only while their creator holds the run lock, which the remover now holds, so the creator is gone). That `dispatch.json` is written before the private copy and the artifact directory it names are created, so a `dispatch` killed at any point of the reservation, while it copies the snapshot included, leaves nothing the next `dispatch` does not remove (a `.marking-<name>` it was killed while marking is removed with it); one killed before `dispatch.json` was written has created neither. A marked directory that cannot be removed keeps its `.reserve-*` record, so the next `dispatch` tries again and the copy is never orphaned: `NOTE  could not remove what a dispatch that ended before it reserved its call left (<error>); no review used it, and its record <reserve directory> is kept so that the next dispatch removes it`. The same holds for a `dispatch` that fails while it reserves and cannot remove what it made: it keeps its own `.reserve-*` record and prints `NOTE  could not remove the private snapshot copy <dir> (<error>)` (or `the artifact directory <dir> (<error>)`, both joined by `or`) `; no review used it, and its record <reserve directory> is kept so that the next dispatch removes it`. A marker that is not a regular file of at most 4096 bytes (a link, a FIFO, a directory) is never followed or waited on: the directory and the record are kept and the error says `<error>; it is not a marker planloop wrote, so <directory> is kept: remove it by hand once no planloop process runs if it is a leftover`. (A private copy `r-XXXXXXXX` or an empty `calls/<call>-r-XXXXXXXX` directory left by a planloop older than this is not found: nothing reads it and it can be removed by hand, `chmod -R u+w` first.) Running `receipt` again on a call that has one re-verifies it and prints it again; when the stored receipt differs from a fresh verification (a declared input changed, or was restored, after the receipt was written) it verifies the call once more with the stored receipt's own revalidation outcome (its `revalidation` list and its `live inputs could not be revalidated` reason, if any) in place of the live one, and only if that reproduces the stored receipt exactly, `created_at` aside (every other field, the reasons and their order, `infrastructure` and `status`), it prints the stored receipt, exiting as for its recorded status, with `NOTE  this is the receipt as recorded; the live inputs revalidate differently now (...) than the receipt records (...)`, and never rewrites it, so a re-run never turns an invalid receipt counted; any other difference, including a `status`, `infrastructure`, `reasons` or `revalidation` that do not follow from one another, is a CONFLICT (exit 3) that prints no receipt and leaves `receipt.json` unchanged; a `receipt.json` edited consistently in every field cannot be told from the original, since nothing else records what the live inputs were at the time (the private copy its own receipt removed is not re-checked: whether the snapshot had changed is taken from the recorded receipt, and a first receipt always checks it; `gate` re-derives the latest gate receipt the same way when it is not counted, so a later invalid gate is reported with its own reasons, while the latest counted gate's copy is kept and always re-checked). A receipt recorded before the reason it re-derives to was worded as it is now (for example `runner left no artifact directory` where `calls/<call>/claudex-*/result.json` exists, from before the `call.json is missing` reason, or from a dispatcher that died while its runner went on to write one) is a CONFLICT on every re-run, yet it still stands as recorded: invalid, never counted, and the next attempt dispatches normally.
6. When the run lock cannot be released (an I/O error renaming `.lock`), a command whose work completed exits 2 saying so (`<what was done>; the lock <path> could not be released (<error>; if it is still there, a planloop command run after this process has exited breaks it)`), printed below the command's own output; a command that had already failed keeps its own error and prints `NOTE  could not release lock <path> (...)` instead. A release whose rename reported an error but took effect (`.lock-released-<nonce>` holds this command's owner) is a release, not an error. A lock that is no longer this command's at release (its `owner.json` reads another owner, is gone or unreadable) is left alone: a command whose work completed exits 3 saying `<what was done>, but lock <path> is no longer ours (...)`, a failed one keeps its error and prints that as a NOTE. In `dispatch`, a failure releasing the lock after the call is reserved means Codex has not run: the message gives the `receipt` command that records the attempt invalid and the next attempt to dispatch; a failure after the receipt is written says the review is recorded and how to print it again. A `gate --publish` that found the plan not approved says so (`the gate found the plan NOT APPROVED (see the output above); the lock ...`). A lock that cannot be prepared (its directory or temporary directory cannot be made) or taken for a reason other than another holder stops the command unverifiable (exit 2) with the error, and so does a stale lock whose breaker cannot make `.lock-break` (nothing is taken; remove `.lock-break` if it exists once no planloop process runs); a lock released just as the timeout runs out is tried once more, a `.lock` whose `owner.json` does not read is never broken automatically (exit 3, naming the directory to remove by hand once no planloop process runs), a lock still held at the timeout is a CONFLICT (exit 3, `<path> is held by <owner>; ...`) that, when its owner is on this host, adds `if process N on this host is not a running planloop command, remove <path> by hand` (`if the process its record names (<value>, which cannot be checked) on this host ...` for a pid planloop cannot check; a zombie owner is dead, so its lock is broken), and a lock breaker that cannot remove `.lock-break` prints a NOTE to remove it by hand.

**Rubric, every round**: contradictions; missing requirements (every obligation row); incorrect assumptions; affected call sites; architectural incompatibilities; failure/recovery; concurrency/order/idempotency; migration/backward compatibility; test coverage; missing failure scenarios; verifiable acceptance criteria; unnecessary scope expansion; **oracles reuse production logic** (an acceptance check that re-derives eligibility, windowing, ownership, calendar or adjudication logic instead of executing production SQL/code kept byte-identical by a CI assertion is a finding); **stateful mechanisms** trace crash mid-step, timeout, partial write, retry, duplicate delivery, reordering, concurrent writers and rollout overlap, or say why not applicable; **every claim the system's output makes must be one the data supports** (for JADE analytics: every rate with its counts, friction used as a rank, never a result). **JADE invariants, every round:** CLAUDE.md rules 1 to 6 hold on every path the plan adds or changes (no child accounts, names or free text; zero activity stored with logging off, and `p6-nolog-invariant` neither skipped nor weakened; class and kit from the session only; no plain codes, tokens or IPs stored or logged; no third-party origin; step ids permanent and edits version-bumped); every new route is in the authorization matrix; every new table with a `kit_id` is covered by `delete_kit_data` and its enumerating test; event or table shape changes bump `catalog_version` and update the generated docs and consent appendix where they add a new kind of information; migrations are forward-only and compatible with the previous release; decisions in `DECISIONS.md`/`docs/adr/` are followed, not reargued. Findings need a severity and concrete evidence; unsupported findings are sent back. The planner cannot waive a finding or accept a residual risk.

## Plan size and shrink-only revisions

**Units and threshold.** A plan's size is the byte length of the `plan.md` planloop stores for the revision (exactly what `plan_sha256` hashes); 1 kB = 1,000 bytes and every size is printed in exact bytes. The threshold is `SIZE_THRESHOLD_BYTES = 250000` in `planloop.py`, recorded in every handback the tool stages (`cut.threshold_bytes`); a run keeps the threshold its first policy revision recorded. The renewal margin is a tenth of it, 25,000 bytes. Changing the constant is a change to this skill, effective for runs whose first policy revision is staged afterwards; per-run relief is only Mike's size decision.

**The report.** `publish` prints `size: revision N is X bytes (1 kB = 1,000 bytes); ...` with signed absolute and percentage growth against the previous revision, revision 1 and the latest shrink-only revision, then `size policy: threshold ..., renewal margin ...; within the threshold | WARN over the threshold by X bytes; gate: eligible (<basis>) | NOT eligible: <what is needed>; meaning: ...`. The same lines come from a recovery that rolls a revision forward (stderr), `publish --recover`, every `dispatch` and `gate` on a policy head, so a revision is never reviewed or approved without its report. `handback --check` and `handback` print the size line against the previous revision, the policy line without the gate clause, the classification, and a `WARN` when the plan is over the threshold; a working, focused or adjudication dispatch on an oversize plan warns and proceeds.

**Classification.** A revision is **shrink-only** when it answers no finding that is open or reopened at handback and loses something of the previous revision: a non-blank line of a section (the lost-line rule of `references/handback.md`), a line of the preamble (the title and every line above the first heading, compared without the title's revision and date), or a whole section. `## Change log` and `## Artifact inventory` are never compared: the inventory holds only heading and id entries and the change log is replaced by every revision, so state every requirement in a section or the preamble. Whether the size fell is reported, not part of the classification, so a correction that rewrites text without answering a finding is shrink-only too. The classification is recorded in `handback.json` (`cut`), with the live answers it rests on (`cut.live_answers`) and the run's threshold. `bundle`, `publish` (before its rename) and a recovery's roll-forward re-check the staged `cut`: its shape, and the lost lines, removed sections and shrink-only flag recomputed from the staged plan and the previous revision given the recorded live answers, each of which the plan's change log must answer and must be a finding of this run (at `bundle` and `publish`, one still open or reopened; at a roll-forward only an existing one, since states may have moved since); `threshold_bytes` must be the run's threshold (the first policy revision's, or the constant for the run's first policy revision). Finding states can change between handback and bundle (an ingest, a `findings decide`), so the live answers are taken as recorded at handback, not re-derived, and one that has since left open or reopened is refused (re-run `handback`); omitting a real live answer only makes a revision shrink-only, which adds a meaning check, so the list is not checked for completeness; once published they are bound by `handback_sha256` like the rest of the record. A `cut` that does not hold is refused (re-run `handback`). Only a cut that, read successfully, disagrees with the authenticated plan and records is refused or moved aside: when Beads cannot be read to check the live answers (a failed, malformed or undecodable `bd` reply, or no run bead), the command stops unverifiable (exit 2), refuses nothing as a bad cut and moves nothing, and the next command retries. `publish` and a recovery check the cut on the bytes they verified, write `HEAD` from that verified `revision.json`, and `publish` refuses (exit 3) when the renamed revision no longer holds those bytes. A shrink-only revision needs a `PRESERVED <ID>: ...` change-log line for every id inventoried in both revisions; an input refresh (the previous plan with only the title's revision and date changed) is not shrink-only.

**The meaning check.** `bundle` freezes, for each shrink not yet judged, the plan before and after it (`.planloop-bundle/meaning-r<S>/before.md`, `after.md`) and a navigation index of every changed unit: lost, edited, added and reordered lines, and added, removed and moved sections. The index and every other mechanical output say what changed, never that meaning survived. Every review carrying the obligation, gate included, has the mandate in its dispatch record and feedback: the reviewer judges each changed unit against the revision before the shrink, writes one `meaning revision <S> <unit>: preserved|changed` coverage line per unit, and raises every semantic difference as a finding (`changed` needs a finding in the same response); a missing, duplicated or malformed line voids the call. The receipt records the verdicts. Differences are ordinary findings, closed only by a FIX verified by a later round, a withdrawal the gate confirms, or Mike's finding decision. Timing: a shrink-only revision can be handed back only when no high or medium finding is open, usually right after a FIX revision is published and before its round.

**Carried obligations.** Publication is never refused over an unjudged shrink. When its own round cannot count (expired observation, a changed declared input, a lost snapshot, a blocked run, a text change forced by the obligations or a late finding), publish the successor the inputs need, an input refresh or a revision that changes the text: its bundle freezes the shrink's comparison again and its reviews carry the mandate, and `publish` prints `NOTE  revision S has no meaning judgement yet; its comparison is carried ...`. Only a counted receipt with valid verdicts for every unit discharges it; a later shrink, a refresh, a size decision and Mike's finding decisions do not, and approval waits for it.

**Gate eligibility and renewal.** A policy head reaches the gate when its plan is within the threshold; or, after an anchor (a judged shrink-only revision that brought the plan from over the threshold to within it), while it stays within threshold + margin; or under a covering size decision. The renewal holds only while every policy revision after the anchor, up to and including the head, stayed within threshold + margin: once one goes past the margin the renewal has lapsed, and coming back under the margin does not restore it. Then another judged shrink back within the threshold (a new anchor), or a decision, is needed; the refusal says which revision ended the renewal. cgr.pl1 under this rule: revision 16 at 459,353 bytes is over; revision 17 at 304,913 is shrink-only but still over, so it is no anchor, and revisions 17-20 would have needed a second shrink to 250,000 or below or Mike's size decision for revision 17 with a ceiling of at least 339,270 (revision 20). `dispatch --kind gate` refuses an ineligible head, naming what a size decision would need.

**The size decision.** When a safe shrink cannot meet the threshold, Mike records `decisions/S<n>.json` (`planloop-size-decision/1`, `references/formats.md`) bound to a judged shrink-only revision's `plan_sha256` with a `ceiling_bytes`; that shrink need not have reduced the bytes (its `PRESERVED` lines can outweigh its safe cuts). It gives a basis only when it names a judged shrink-only policy revision at or below the head with that hash and a ceiling at or above both that revision's size and the head's; a well-formed one that gives no basis is a NOTE and fails nothing, a malformed one fails readiness and the gate dispatch. The lowest-numbered covering decision is selected and bound into the approval by its file hash, so adding a valid, covering decision with a lower number after the approval changes the selected basis and lapses the approval (deliberate: the approval binds the lowest-numbered covering decision). Only a file named exactly `S<positive integer>.json` in `decisions/` is a size decision; any other `S*.json` there is ignored with a NOTE and fails nothing. A size decision never closes or accepts a finding, never waives a meaning judgement and never changes another run's threshold; a meaning change survives only through Mike's ordinary finding decision.

**The policy range.** A run's policy starts at its first published revision whose `handback.json` has `cut`, which is the first revision this tool staged; earlier revisions, and runs that never publish again (every run approved before the change), are outside it and verify exactly as before. Nothing is written to `run.json`. Every policy fact is derived only from revisions authenticated from HEAD's pointer: each command that derives the policy first verifies every published revision from 1 to HEAD with the existing revision check, once per command (again only after the command itself moves HEAD), deriving everything from the bytes that walk hashed, so an edited `plan.md`, `handback.json`, `revision.json`, manifest or frozen copy (`bundle/frozen/`: each file a manifest item names, checked against that item's sha256, `record_sha256` or `before_sha256`/`after_sha256`/`index_sha256`, plus each evidence record's output copy `evidence/<output>` against that record's `output_sha256`, a missing one included; a frozen path a manifest names that is not a string, is empty, starts with `/`, contains a NUL or a backslash, or has a `.` or `..` component is the failure `revision N manifest names an unsafe frozen path`, never a read outside the bundle), or a manifest whose plan item is not `plan_sha256` is an integrity failure (the run's problem, not a draft's; inspect by hand), never a policy that disappears, starts elsewhere or changes (a record in that walk that exists but cannot be read, a permission or I/O error, is not one: every command, `gate` included, stops `UNREADABLE` with exit 2 and records nothing): `gate` without `--publish` reports it as a failed check and prints NOT APPROVED (exit 1); `gate --publish` and every other command stop with exit 2 (their recovery walks the chain first). A malformed manifest (no `items` list, an item that is not an object or has no `type`, an overlay entry or snapshot item without its fields, bytes that are not UTF-8) or a missing `plan.md`, `handback.json` or manifest is one such failure, never a traceback. Once that walk passes, a failed deep check of HEAD itself (its frozen snapshot missing or changed) is a plain failure: `dispatch` exits 1 and `gate`, with or without `--publish`, reports it and prints NOT APPROVED (exit 1). A stored receipt whose binding to the authenticated revisions fails is reported as that (`inspect that receipt`), not as a broken chain, and fails closed the same way. Receipts, dispatch records, decisions and Beads are written after publication: a receipt judges a shrink only when it and its dispatch record are bound to that chain and its mandate equals the frozen obligation, and its content is otherwise trusted as stored receipts are today.

**Processes running older planloop code.** A process started before the change keeps its code. What it can do on a policy run grants nothing: a revision it publishes without `cut` is classified from its text (shrink-only exactly when it lost anything), reported with a `NOTE  revision N was published by planloop code that predates the size policy`, refused for dispatch while it owes an unfrozen comparison (`stage, bundle and publish a successor with the current tool`), and judged through that successor; a round it dispatches judges no shrink; an approval it writes lacks the size facts and does not hold (`state --set active`, then re-gate); its `receipt` on a mandated call fails without writing. A staging it handed back is refused by `bundle` and `publish` (re-run `handback`). A publication it left interrupted (a `rev-NNN` above HEAD) has no publishing intent, so recovery moves it aside rather than rolling it forward; re-stage it with the `handback` command the NOTE gives.

## Recurrence and escalation (mechanical where marked)

| Trigger | Response |
|---|---|
| A round shows the work touches a risk domain the classification missed (any finding, or the planner's own discovery) | re-run `init --track escalated` with the added domains and a rationale; the escalated planner policy and Codex high apply from then on, and the next revision (`planloop_escalated_revision` = HEAD+1) is drafted by Fable |
| A finding unresolved after two proposed fixes | **mechanical**: `planloop_redesign_required`; the next handback must answer it with `REDESIGN`, which raises the floor to high |
| The same finding needs a second redesign | **mechanical**: track becomes escalated (escalated planner policy, Codex high); `planloop_escalated_revision` = HEAD+1, so Fable drafts the next revision |
| A verified finding reopens | **mechanical**: floor rises to high; the next brief asks for an interaction review of everything the fix touched |
| A HIGH after a clean round or a passed gate | the clean result is void: the gate must be the latest call and every finding must be closed |
| The same named invariant (`INV<n>`) is broken in two distinct rounds, under any finding ids | **host obligation**: treat as a redesign trigger and answer with REDESIGN; the tool tracks findings, not invariants |
| Planner and reviewer still disagree after a revision | an `adjudication` call with the planner's assumptions and failure trace; if the evidence cannot settle it, gather the evidence; if it is a judgement only Mike can make, `needs_decision` |

A **structural redesign** names the mechanism replaced, why each earlier fix failed, the new mechanism, and its invariants and failure traces. A patch labelled "redesign" is a finding against the revision. None of these triggers ends the run.

## Evidence

**What reaches Codex.** Bundles, briefs, evidence outputs and the snapshot are sent to an external reviewer. They must never hold pilot data (rows from a staging or production `events`, `kit_progress`, notes, quiz or exit-card table, or a real kit id tied to a class), adult emails, plain kit or join codes, tokens, `CODE_PEPPER` or any other secret, or a `.env` file. Use the demo kit, seed data and fixtures. Check that `.env*` (other than `.env.example`) and code-card or packing-CSV output directories are git-ignored before the first bundle, since the snapshot overlays every untracked non-ignored file.

Each record (`planloop-evidence/1`) states its claim, query/code and hash, inputs and hashes, source, observation window, collection time, snapshot identity, group, status, limits, truncation, attempts and validity. Rules:
- **empty** (success, zero rows) needs a match proof; **unknown/error/timeout** supports nothing; truncated output cannot support a completeness claim.
- At most three attempts (two retries), backing off at least 5 s then 15 s.
- Default limits 1,000 rows / 1 MiB; larger needs a written justification; hard cap 100,000 rows / 64 MiB.
- A group shares one snapshot (one `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY` transaction, `statement_timeout 3s`, `lock_timeout 250ms`); one failed member means the whole group is recollected.
- Validity: `historical` (an observation of a past window; never expires with time), `until_input_change` (invalid when an input hash changes), `observation` (a claim about current state: valid while `dispatch time − collected_at ≤ max_age_s`, checked at every dispatch; an expired one must be recollected into a new revision).
- **What an approval certifies about observations.** By default an observation is certified **as of the gate's dispatch**: the approval record lists it with its collection time and that instant, and it does not lapse later. An observation marked `must_remain_current` is a condition the approval depends on staying true: it is re-checked against the clock at publication and at every later `gate` re-verification, and the approval visibly lapses when it expires. Use the flag only for such conditions, with a `max_age_s` that covers the gate, or approval will keep lapsing.

## The final gate and approval

1. Re-run step 0; republish (new revision) if anything changed.
2. `dispatch --kind gate --effort high` on the published revision. The feedback asks for an independent full-rubric review; earlier approvals are not evidence.
3. `findings ingest` for the gate (an empty map if it found nothing). Low findings at the gate are findings: they must be closed (verified by a later round, withdrawn or decided by Mike). The gate is shown every withdrawn finding's original failure scenario and withdrawal evidence and must answer `withdrawal confirmed` or re-raise it; an unconfirmed withdrawal blocks approval.
4. Record Mike's acceptance of each material residual risk: `plans/planloop/<run>/decisions/D<n>.json`, his exact words, `text_sha256` of the RR line. Deferred findings name their follow-up bead.
5. `gate --run R --publish` checks every item in "What is enforced" (for a policy revision also that every shrink-only revision since the size policy applied has a counted reviewer's meaning judgement and that the head is gate-eligible under the size policy; the approval record then binds the size facts, the selected size decision's file hash and every judgement's receipt hash), then: writes the pending approval record → records it in Beads as the candidate and reads it back → re-runs every readiness check → replaces the `APPROVAL` pointer → marks the run bead approved. A crash before the pointer leaves only an unreferenced pending record; a crash after it leaves Beads lagging, which `gate` reports and `gate --publish` completes. The pointer is the only thing that means approved, and `gate --run R` re-verifies it against current state (an input change afterwards voids it). Once it no longer verifies, `state --set active --reason ...` reopens the run for a new revision and a fresh gate; a run whose approval still holds cannot be reopened.
   **claude backend.** Step 2 is a fresh Opus `Plan` agent of kind `gate` at high effort, recorded with `receipt --transcript` as above. Before step 5, show Mike the plan and the gate review; record his words with `signoff --run R --quote "<his exact words>"` (it writes `decisions/A<n>.json`, `planloop-signoff/1`, bound to the revision's `plan_sha256` and the gate receipt's sha256; a hand-written one must have the same shape). Readiness then also requires a sign-off bound to exactly that revision and gate receipt (a well-formed one bound to another is a NOTE), the gate to be a claude call dispatched after the run's last backend change, and its transcript to re-verify from the kept copy; the approval record adds `reviewer_backend` and the sign-off file's hash, so an edited sign-off lapses it. `gate --publish` also appends the gate outcome (call, model, effort, verdict, findings, receipt hash) and Mike's words to the run bead's notes. Every other readiness check is unchanged. For `codex`, nothing in this paragraph applies.
6. Report the approved plan to Mike for sign-off. **Plan approval is not implementation authorization and never closes the implementation bead.** Implementation waits for Mike's explicit go-ahead.

## Beads

The run bead (`run:<run>` key, child of the implementation bead) holds run state, track, effort floor, redesign flags, blocker reason and approval. Each finding is a child bead with key `finding:<run>:R<k>`; its metadata holds state (`open`, `fix_proposed`, `reopened`, `verified`, `withdrawn`, `decided`), severity, raising call, fix and reopen counters, lineage and its resolution reference; it is closed exactly when resolved. Beads allocates the ids (`--parent`); the logical key and a per-write nonce live in metadata, so a create that races another writer, or whose reply was lost, is detected on read-back instead of overwriting anything (`bd create --id` silently overwrites, so it is never used). Every change is planned as an intent file (`intents/`), applied idempotently, read back and marked verified; any locking command replays unfinished intents first, and approval is blocked until none remain and `findings check` passes. Only the orchestrator runs `bd`, always through these commands (a planner's `handback --check` issues only `bd show`/`bd list` and planloop writes nothing, though bd's embedded Dolt may update its own bookkeeping files such as `.beads/last-touched` on a read): never SQL against Dolt, never `.beads/issues.jsonl`, no remote sync without authority.

Files keep the exact plans, bundles, evidence, receipts and decisions; Beads keeps status. `ledger.md` is a generated projection of both and is never edited. On resume after compaction or interruption: `ledger --run R`, `findings check --run R`, read the latest receipt, then continue.

## Limits, stated plainly

- **Threat model** (Mike, 2026-11-13). planloop defends against accidents: a crash or kill at any point, races between its own commands, reboots, ordinary containers, sandboxes and other namespaces, and a systemd, bus or filesystem that is slow or fails. It does not defend against a hostile process running as the same user: one that forges `/proc`, bind-mounts over cgroup files or plants FIFOs or links can fool it or make it refuse. The mount proof (cgroup2 root by `mountinfo`, same `mnt_id` at every level), the procfs checks on `mountinfo` and `fdinfo`, and the regular-file and size checks on control files and markers are accident hardening that turns a confusing environment into a refusal; they are not a security boundary.

- **Effective effort** is what the Codex CLI recorded in its rollout `turn_context` for the turn. The provider's server-side compute is not observable; the check proves the CLI was configured and sent `high`, not more.
- The rollout format is undocumented. `scripts/codex_rollout_versions.txt` lists validated Codex versions; any other version is **unverifiable**, so after a Codex update reviews stop counting until one real review is checked with `planloop.py rollout-check --artifacts <runner dir> --accept` (it validates the structure and settings, then records the version). An unfamiliar structure fails that check; update the parser and its fixture instead.
- On drvfs a rename fails with EACCES while any file inside is open (an editor, an indexer); planloop retries for a few seconds, then reports a conflict without having changed anything.
- Re-verifying an approval needs the runner artifacts and snapshot under `~/.local/state/planloop/<run>/` (Codex's own rollout may be pruned; the kept copy is then used). Do not clean that directory for a run you may still need to re-verify. Old snapshots are read-only: `chmod -R u+w` before removing one.
- The lock and atomic renames assume one host. Every lock owner (`.lock`, `.lock-bundle`) and `running.json` records its host, boot id, PID namespace (the inode of `/proc/self/ns/pid`), process id and process start time, and an owner is taken for dead only on this host and either after a reboot (another boot id) or from the PID namespace it recorded, where its process id is gone, exited or belongs to a process with another start time. A container, a sandbox that unshares the PID namespace or another WSL distribution sharing the checkout has the same host name and boot id and other process ids (so does the same WSL distribution after a restart under a still-running VM: it keeps the boot id but gets a new PID namespace, so a lock or `running.json` a crash left before that restart is removed by hand), so from there a live owner's process id is absent or names an unrelated process: a lock whose owner names another PID namespace, or none (a lock left by a planloop older than 2026-11-13, which is therefore removed by hand after a crash), is never broken automatically. The command waits for it up to the lock timeout, then stops `CONFLICT`, exit 3, printing the owner record, both namespaces and the way out: run the command where the lock was taken, which breaks it if its owner is dead, or check there that the process is not a running planloop command (or that nothing of that namespace runs any more: from outside it, `lsns -t pid | grep <pid_ns>` lists the namespace while anything of it runs), then remove the lock by hand; when the same process also holds the other planloop lock (`.lock-bundle` or `.lock`: the same host, boot, PID namespace, pid and start), the CONFLICT names it too, to be settled the same way. A lock held from another host says to check on that host that its process is not a running planloop command, then remove the lock by hand. `publish --recover` that leaves a `.lock-bundle` it could not break prints `NOTE  <lock> is held by <owner> and publish --recover left it` with the same advice. A process that cannot tell its own PID namespace (`/proc/self/ns/pid` cannot be read, or `/proc` is not mounted for its PID namespace, as under `unshare --pid` without `--mount-proc`: `/proc/self` is not its pid) records `pid_ns` null, so its locks are never broken automatically, and `dispatch` refuses there (UNVERIFIABLE, exit 2, before it reserves anything). A lock held from another host is never broken automatically either, nor one whose owner's process is still alive when its start time could not be recorded (so a process id reused by an unrelated process keeps it: the CONFLICT then says to remove `.lock` by hand if that process is not a running planloop command; when the owner runs with the start time it recorded, it says instead that the process took the lock and is alive, to wait for it or stop it; an owner that has exited but is not yet reaped is dead); a crashed lock breaker leaves `.lock-break`, which an operator removes after checking no planloop process runs.
- The reviewer's sandbox can read the whole filesystem, so isolation is detection, not prevention: shell commands are checked for relative climbs above the copy's root and for absolute references to the checkout, planloop's state directories or `~/.codex`. Quoted paths, `(…)` subshells and a `cd` into a directory that does not exist are handled. Not detected: a path computed at run time (`cd $(dirname $PWD)`), a path through an unrelated symlink, a command run in a working directory the event log does not show (planloop assumes the copy's root, which errs toward flagging), and reads by non-shell tools that take no path. Checked on 2026-10-23 against all 30 commands of a real Codex gate review: no false positives. The isolated root must live on a filesystem that honours permissions (the default, `~/.local/state`, is ext4); `dispatch` refuses one that stays listable after `chmod 0300`, as drvfs `/mnt/c` without the `metadata` mount option does. Only the latest counted gate keeps its private copy (re-verification needs it); every other copy is removed once its receipt exists. If that copy is lost, `gate` reports the approval as lapsed and `state --set active` reopens the run for a fresh gate.
- **claude backend.** The transcript and its meta are files Claude Code writes in `~/.claude/projects/<project>/<session>/subagents/`; planloop verifies what they record, not how it was recorded: the model and effort (Claude Code records both per turn and per API request, checked as of Claude Code 2.1.325, where a `Plan` agent launched with `effort: "high"` records `high` in its meta and on every turn) are **host-attested** by Claude Code, and the provider's server-side compute is not observable. That the orchestrator gave the prompt verbatim is mechanical only as far as the first user turn matches; that the agent read the plan and feedback in full is not proven (opening each is). Isolation is detection: the agent's tools can read the whole filesystem, and a path computed at run time or a write by an interpreter's inline code is not detected. The transcript format is undocumented (parser `claude-subagent/1`, fixture `tests/fixtures/claude-code-2.1.325-subagent-shape.json`); an unfamiliar shape is unverifiable, never counted. There is no claude triage call. A kept transcript or receipt edited consistently cannot be told from the original, as for Codex.
- Discovery completeness, the truth of Mike's recorded words, and the semantic quality of the plan remain judgement and host obligations.
- The meaning check of a shrink is a reviewer's judgement, recorded and bound to the frozen texts, never proven right. Lexical aids were measured on cgr.pl1 revisions 16 and 17 and the rejected draft: a qualifier-word flag marks about 94% of a shrink's lost lines and scores the rejected draft and the corrected revision almost identically, so planloop offers none.
- The tree hash of a snapshot covers regular files and symbolic links (to files or directories), not empty directories: an empty directory added to or removed from a snapshot or private copy is not detected (it holds nothing a reviewer can read; hashing it would change the recorded hash of every existing snapshot that has one, such as a directory emptied by an overlay deletion).
- `receipt.json` is trusted as the record: a receipt edited consistently in every field cannot be told from the original (step 5 of "Each review round", and the receipt format), and hand-editing receipts is out of scope (Mike, 2026-11-11).
- A judging receipt is trusted as stored counted receipts are for finding resolutions: it is bound to the authenticated revisions and mandate and, after approval, by its hash, but a receipt edited before approval would still be read.

## Validation

`python3 .claude/skills/planloop/tests/test_planloop.py [names...] [-j N] [--times FILE] [--timeout S] [--allow-skips] [--serial]`, from anywhere (set `PLANLOOP_TEST_TMP` to run on drvfs too). It runs every test in its own process, a CPU's worth at a time (about 5 minutes instead of 45; `-j N`, `--times FILE` to start the longest first, any unittest names such as `tests.test_planloop.Gate` to run a part), reports like unittest, and fails on a failure, an error, a skipped test (unless `--allow-skips`), anything a test leaves in its temporary directory, and a test that outlives `--timeout` or ends without a result; `--serial` runs the same selection in one process with plain unittest, under the same skip and leftover rules, for debugging. Its options and runner live in `tests/run_parallel.py`. Isolated git repositories, a fake `bd` with bd 1.2.2's behaviour plus a race/lost-write injector, a fake runner that writes the real runner's artifacts and a rollout built from a real codex-cli 0.156.1 record shape, a fake Claude reviewer (`tests/fake_reviewer.py`) that writes a `Plan` agent transcript and meta from a real Claude Code 2.1.325 record shape (`ClaudeBackend`: a valid review, a wrong model, alias or effort, an edited prompt, a resumed agent, write tool calls, paths and commands outside the copy, malformed JSON and coverage, an unfinished agent, the sign-off gate, re-verification after approval, backend switches and a legacy `run.json`), crash points at every publication and approval boundary, and one full run against the real `bd` in a throwaway database. Every dispatch in it starts a real systemd user scope, named for the test's own temporary directory and gone when the test ends, so it needs what `dispatch` needs (`systemd-run`, cgroup v2, the user's systemd manager); the tests of a hidden cgroup tree run in a user and mount namespace of their own and are skipped where this user cannot create one. Run it after any change to this skill.
