# bugfix

The light loop for **one already-verified, bounded defect**. It is not for features, design questions, or anything not yet confirmed by reading the code (verify first: the host verifies every reported bug or finding by reading the code, and reproducing it where possible, before acting on it). When the work stops being bounded, it leaves this skill for `/planloop` (see Routing).

History: established 2026-09-22; severity routing and a closure rule the same day. **Revised 2026-10-23 (Mike, `quartz-rs-p49`)**: the "never a third round" closure limit is gone (the final patch is reviewed until clean); the exact fix is isolated from unrelated edits; dispositions, regression evidence, review and gates are bound to the final artifact; findings live in Beads; commits follow the active authorization. **Revised again 2026-10-23 (`quartz-rs-3bm`)**: review and final validation run on the exact delivery candidate and are bound to its tree hash as well as the patch hash; pre-existing gate failures are compared against the same HEAD without the fix; worktrees are recorded and removed only by `fixpatch.sh cleanup`; the staged tree must equal the validated candidate tree before a commit.

**Adopted for JADE (2026-11-14).** This skill was built for quartz-rs; the history above and the `quartz-rs-*` ids it cites are that project's provenance and are not beads in this repository. The mechanics are unchanged (`scripts/fixpatch.sh`, its tests, the severity table, baseline/patch/candidate/verify/check/staged/cleanup, review bound to patch hash and tree hash, findings in Beads, routing, closure, delivery, resume). What is JADE's: the gates below; the HIGH-by-default cases for CLAUDE.md rules 1 to 6 and Mike's data-impact decision (Severity); the JADE routing triggers and the stop-and-ask for rules 1 to 6 and accepted decisions; worktrees on ext4 with a Compose project each; the review criteria for JADE's concurrency and rules; and delivery that respects staging auto-deploy. Binding project sources: `CLAUDE.md` (rules 1 to 8, bead workflow), `docs/handoff/ARCHITECTURE.md`, `DECISIONS.md` (and `docs/adr/`), `DATA-MODEL.md`, `EVENTS.md`, `PRIVACY.md`. Bug beads are filed as CLAUDE.md says: `bd create "..." -t bug -p <0-3> -l bug` with reproduction steps. **Until Phase 1 lands the gates (`p1-scaffold` for the scripts, `p1-ci` for CI), no fix can reach Closure**: step 6.2 cannot run, so the fix stays open (or is reported to Mike as unvalidated), never closed on targeted tests alone.

**The gates.** Fast: `pnpm lint && pnpm check && pnpm test`. Full: `pnpm e2e` (Playwright, Chromium and WebKit). Both need Postgres: the `p1-db` harness gives each integration test file, and the e2e server, a database of its own on the development database. Gates run from the root of a candidate worktree, after `pnpm install --frozen-lockfile` there; a fresh worktree then needs two more commands before any gate, `pnpm env:init` (writes the worktree's own `.env`, mode 600, with a database port that is free) and then `pnpm db:up` (starts the development database, service `devdb` of `compose.dev.yml`, and waits until it is healthy); the harness migrates its own databases, so no `pnpm db:migrate` is needed. Each worktree gets its own Compose project, `COMPOSE_PROJECT_NAME=bugfix-<bead>-<purpose>`, exported before `pnpm db:up`, which uses the exported name as its project (`-p`), so two gates never share a database, and it is torn down afterwards with `docker compose -p <name> down -v`. `compose.prod.yml` never joins the gate's project: it is brought up only through `pnpm stack:up` (project `jade-stack-<checkout hash>`) or `pnpm test:infra` (projects `jade-infra-<run id>-<test>`), each of which passes its own `-p`, which Compose prefers to the exported `COMPOSE_PROJECT_NAME`, so the gate's `docker compose -p <name> down -v` removes only the gate's development database. Gate output (`.svelte-kit/`, `build/`, `node_modules/`, `test-results/`, `playwright-report/`, coverage output) must be git-ignored, or `fixpatch.sh check` fails after the gate; that is a repository defect to file as its own bead and fix, not a check to skip. If the Phase 1 scripts land under other names, update this skill in the same change.

## Roles

- **Orchestrator (host)**: verifies the bug, assigns severity and risk (the reviewer confirms it; a LOW or cosmetic label is recorded on the bead with its reason), captures the baseline and patches, briefs agents, runs gates, and is the only one who runs `bd`. It does not settle disputed findings, except for LOW and cosmetic fixes where it is itself the reviewer.
- **Implementer**: writes the fix and its regression test; proposes dispositions; never runs the fast or full gates, never commits.
- **Reviewer**: read-only. Never edits, never runs gates. A fresh Opus or Fable agent gives **context independence** (it did not write the fix and sees only the brief and the patch); it is the same model family as the implementer, so it is **not** model diversity. **Cross-model review** means Codex (`runner.py inspect`, static, read-only), used where the table says so.

## Severity and routing

| Severity | Implement | Review of the final patch | Regression test |
|---|---|---|---|
| HIGH | Opus | fresh Fable agent; plus a Codex inspect pass when the bug is in a high-risk domain | required, proven to fail on the original code (see Evidence) |
| MEDIUM | Opus | fresh Opus agent; fresh Fable instead when the fix touches shared/persisted state or an invariant several writers depend on | expected; a missing one needs the documented exception |
| LOW | Sonnet (mechanical, 1-2 files) or Opus (cross-cutting) | the orchestrator's own read of the patch, or one fresh Opus pass if shared code paths are touched | expected where practical |
| Cosmetic / docs | Sonnet | none beyond the orchestrator's read and the gates | none |

**HIGH by default in JADE.** A bug that violates one of CLAUDE.md's rules 1 to 6 is HIGH unless the reviewer and Mike agree otherwise: activity stored or logged for a kit whose `logging_enabled` is false; one kit or class reading or writing another's data (identity taken from a request body, a missing scope); a student, or an adult without the role, reaching a page or record they should not; a plain kit code, join code, token or IP address stored or logged; a request from the browser to a third-party origin; events double-counted or lost (ingest idempotency, offline replay); a changed step keeping its version. Such a bug also goes to Mike as soon as it is verified, before the fix: he decides whether data already collected is affected and what follows (deletion, a note in the data-quality report, telling the school). The fix does not wait for that decision unless he says so.

**High-risk pre-plan (any severity).** If the bug touches recovery, reconciliation, persistence guarantees, ordering, idempotency, session identity, state machines, cross-system consistency, silent corruption or hard concurrency, or JADE's consent gate, privacy, authorization, secrets or a schema migration (planloop's risk domains, including `consent-gate`, `privacy`, `authorization`, `secrets`, `schema-migration`; its "Risk classification" table lists the JADE work in each), or you are unsure, run one fresh Fable agent first for a short mini-plan: fix shape, what it touches, what the obvious fix breaks, what must be preserved. No code. It goes verbatim into the implementer's brief.

## Routing to planloop

Stop this skill and open a planloop run (`planloop.py init --run <bead>.plN --bead <bead> --track ... --risk-domains ... --rationale ...`, escalated for any risk domain) when any of these holds; record the reason on the bug bead:
- the same finding is still unresolved after two corrections, corrections keep breaking the original invariant or an adjacent one, or a third consecutive review raises new related HIGH/MEDIUM findings (record the count of corrections per finding in its notes);
- implementer and reviewer disagree about the mechanism or the architecture and the evidence cannot settle it;
- the fix needs a migration (a new or changed file in `migrations/`, a grant, `delete_kit_data`), an event catalog change in `src/lib/shared/events/` (a new type or field, a `catalog_version` bump), a content-format or `content.lock.json` change, a new route (which needs an authorization-matrix entry), or another new mechanism (a new table, module API, background job or state);
- the patch grows beyond the bug's scope (new files or call sites not caused by the bug).

planloop's gates then apply in full: plan approval, and Mike's separate implementation authorization before any further code. The partial patch stays on disk and in its baseline ref; nothing is reverted.

Two cases are not a planloop run but a stop, as CLAUDE.md requires. A fix that would change or relax one of CLAUDE.md's rules 1 to 6 (rather than restore it) goes to Mike before any further work. A fix that would deviate from an accepted decision (`DECISIONS.md`, `docs/adr/`) is filed as a `decision` bead labelled `human`, and work on the bug stops. Record either on the bug bead.

## Step 0: set up

1. **Bead.** The bug has a bead (create one if not). Claim it.
2. **Baseline.** Before any agent edits anything: `.claude/skills/bugfix/scripts/fixpatch.sh baseline <bead>`. It snapshots the whole working tree (staged, unstaged, untracked non-ignored) into `refs/bugfix/<bead>` without touching the index, the tree or any branch. Record the baseline tree it prints on the bead: `bd update <bead> --append-notes "bugfix baseline tree <hash>"`.
3. **Pre-existing work.** List every path already modified or untracked at baseline (`git status --porcelain`). It is not part of the fix, even in a file the fix touches; fixpatch excludes it by construction. Never reset, stash, overwrite or revert it.
4. **One bugfix per tree at a time**, and the implementer works in this baselined checkout, never with `isolation: "worktree"` (its edits would not reach the patch). Edits made by anyone else after the baseline also land in the patch: report such hunks to Mike, never revert them.
5. **Delivery candidate.** Decide, and record on the bead, what will be delivered: if the fix will be committed, the candidate is **HEAD + the fix** (`fixpatch.sh candidate`), which excludes every unrelated working-tree edit; if it stays uncommitted in the user's tree, it is **baseline + the fix** (`fixpatch.sh materialize`). With a clean baseline (its tree equals HEAD's) the two are the same tree. Review (step 3) and final validation (step 6) both run on this candidate, never on the user's working tree, because an unrelated uncommitted edit can supply a guarantee (a guard, a config value, a helper) the delivered tree does not have.
6. **Worktrees** (`materialize <bead> <patch|none> <dir>` = baseline's HEAD + baseline tree [+ patch]; `candidate <bead> <patch|none> <dir>` = current HEAD [+ patch]) go **outside the checkout on the same ext4 filesystem** (e.g. `~/projects/.bugfix/jade-<bead>-<purpose>`) and are created with hooks off. Each prints `... at <HEAD> tree <T>`; record that line on the bead. fixpatch records every worktree it creates for the bead (in the repository's git dir, with an owner nonce) and **only `fixpatch.sh cleanup <bead> [<dir>...]` removes them**: it refuses any path it did not create for this bead, a path since reused by someone else's worktree, and a worktree a running process is using (cwd or open file: a gate still running there). That scan sees only processes this user can read. A Docker container (the gate's Postgres, which runs in the Docker daemon, not as a process in the worktree) or a Playwright browser left behind by a killed gate (a Bash tool timeout, for example) can survive it, so after a gate timed out or was killed, check `docker ps` and `docker compose -p bugfix-<bead>-<purpose> ps`, and stop them (`docker compose -p <name> down -v`, and any leftover browser processes) before cleanup. Never remove a worktree with `git worktree remove` yourself, never one you did not create, and never validate by changing the user's tree.

## Step 1: implement

One non-fork `Agent` with the table's model. Brief it as CLAUDE.md requires (a subagent starts cold): the hard constraints; the exact files and line ranges to read itself; the verified mechanism and failure scenario in full; the mini-plan if any; the in-scope paths and the pre-existing work it must not touch. Its job, in order: confirm the bug in the code; find the root cause; make the smallest correct fix; add a regression test that reproduces the original failure; run only targeted validation (`pnpm vitest run <file> -t "<name>"`, `pnpm playwright test <file> --project=chromium`, scoped `pnpm eslint <files>` and `pnpm prettier --check <files>`), never the full gates, never `git commit`. A needed migration, event catalog change, content-format or `content.lock.json` change, new route, or anything touching CLAUDE.md rules 1 to 6 beyond restoring them is not made: it stops and reports (→ Routing). It reports what changed, what it read, the root cause, the test and what it proves, its validation output, and every judgement call.

## Step 2: capture the exact patch

`fixpatch.sh patch <bead> ~/.local/state/bugfix/<bead>/patch-<n>.patch` (a new `<n>` each time; never the scratchpad, a later session must find it). fixpatch creates the directory (mode 700) if it is absent, never replaces an existing file (a reused name exits 2 and leaves the earlier patch as it was; earlier patches are evidence, keep them), and writes nothing when the path is invalid (inside the checkout, through a regular file, or an existing directory). Record `patch <n> sha256 <hash>` on the bead. Then build the delivery candidate for this patch (step 0.5) and record its tree `T`: `patch <n> sha256 <hash> candidate <kind> head <HEAD> tree <T> dir <dir>`. Check the printed file list against both the scope and the implementer's list of files it touched: an out-of-scope path is either caused by the bug (keep it, say why), the implementer's stray edit (send it back), or someone else's edit (report to Mike, never revert). A touched file missing from the list is **ignored by git** and is not in the patch: it needs a stated exception (and separate delivery) or a different fix. This checkout is on ext4 with `core.filemode=true`, so an executable bit the fix sets appears in the patch and the candidate tree `T` like any other change; check it is intended. Only on a checkout with `core.filemode=false` (a filesystem that does not keep exec bits), a file that must be executable shows as mode 100644 in the patch and in `T` alike: there, record its path on the bead as `exec <path>`, and set the bit only at delivery (Delivery step 3). This patch, and only this patch, is what gets reviewed, validated and delivered.

## Step 3: review the patch

One read-only reviewer per the table. Give it the bug report, the invariant to restore, the patch file and its hash, the **delivery-candidate worktree path and its tree `T`**, and the list of pre-existing unrelated work that the candidate does or does not contain. It reads the code **in the candidate worktree**, not the user's checkout, so it judges the tree that will be delivered; any claim that rests on code present only in the user's working tree is a finding. It expands into callers, siblings and fixtures only to check a specific claim. It looks for wrong assumptions, missed cases, regressions on correct paths, concurrency/state issues (in JADE: two devices redeeming or joining with one code at once; retried, duplicated or out-of-order ingest batches; a whole class behind one public IP, for rate limits and lockouts; the logging toggle flipping while events sit in a device's offline queue; a kit's devices reset mid-batch), and whether the regression test reproduces the real failure. It also checks that CLAUDE.md's rules 1 to 6 still hold on every changed path, that any new route is in the authorization matrix test, that any new table with a `kit_id` column is covered by `delete_kit_data` and its enumeration test, and that `p6-nolog-invariant` is not skipped, weakened or deleted (any of these failing is a finding). It also confirms or disputes the severity label. It returns findings, each with severity, file/line, concrete failure scenario, confidence and a direction, or says "clean". Record the outcome on the bead: `review <reviewer> patch <n> <sha> tree <T>: clean` or the finding ids. Before recording it, `fixpatch.sh check <dir> <T>` must pass (the reviewer is read-only, so a failure means someone edited the candidate: the review is void). On a correction round it reviews the **new whole patch** in a new candidate, with the previous patch's hash, so interactions with earlier edits are in view.

**Related** means caused or left open by this fix: the fix introduces it, the fix exposes an unsafe interaction (even in another file or another failure path), or the original invariant is not fully restored. A related HIGH or MEDIUM finding blocks closure. **Unrelated** means independent of the fix: it becomes its own linked bead (`bd create ... --deps discovered-from:<bead>`) and does not expand this patch. When in doubt whether a finding is related, it is related until the reviewer or Mike says otherwise.

## Step 4: findings and dispositions (Beads)

The orchestrator records each finding as a child bead of the bug: `bd create --parent <bead> --title "[sev] F<n>: <claim>" --type bug --metadata '{"bugfix_finding":"F<n>","bugfix_state":"open","bugfix_severity":"<sev>","bugfix_patch":"<sha>"}' --silent`. Look the finding up first (`bd list --parent <bead> --all --json`) and never use `bd create --id` (it silently overwrites an existing id). Finding ids are stable for the life of the bug; a re-raised finding keeps its id.

The implementer proposes, for each finding: **accept** (and fixes it), **reject** (with code or test evidence against the failure scenario), or **investigate**. A proposal is not a disposition:
- an accepted finding closes only when a later review of the corrected patch says it is resolved;
- a rejection closes only when the reviewer accepts the evidence, or Mike decides; record which in the bead's notes and close it with that reason;
- anything still uncertain stays open.
Record dispositions with `bd update <finding> --append-notes ...` and `--set-metadata bugfix_state=<state>` (values are coerced by bd: keep them plain words), then `bd close <finding> --reason "<resolved in review of patch <sha> | rejection accepted by <reviewer|Mike> because ...>"`.

## Step 5: correct and re-review until clean

Every correction produces a new patch (step 2), a new candidate tree, and a new review of that whole patch in it (step 3). Once HEAD has moved since the baseline, a correction goes to Mike instead (step 6, head-moved route). There is no round limit; the Routing triggers are what end an unbounded loop, by moving it to planloop, not by closing early. Infrastructure failures (an agent or Codex call that errors or times out) get at most two retries with a stated change; an unchanged blocker is reported to Mike, not retried.

## Step 6: evidence and gates on the exact artifact

Before running anything, and again after the gates and before staging, `fixpatch.sh verify <bead> <final.patch> <sha recorded at the clean review>` must pass: the tree still holds exactly the reviewed patch, the file still hashes to it, and HEAD has not moved. `verify` checks HEAD first. If HEAD moved (someone committed, pulled or rebased mid-fix), stop and ask Mike, showing `git log --stat $(git rev-parse refs/bugfix/<bead>^)..HEAD`, and **do not run `patch` again**: diffed against the old baseline, a new patch would absorb the new commits. If he confirms the new commits are unrelated to the fix, record his decision on the bead (`head-moved route: <old HEAD> -> <new HEAD>, Mike <date>`); the reviewed `final.patch` stays the delivered artifact. This route is for HEAD + fix (commit) delivery only; an uncommitted (baseline + fix) delivery after a HEAD move goes to Mike. On this route a review finding that needs a correction also goes to Mike: neither `patch` nor a new baseline can produce a clean corrected patch. Build `candidate <bead> <final.patch>` at the new HEAD (a new `T`; if it does not apply, ask Mike), redo the review and every check below on it, and from then on `check` on that candidate and `staged` at delivery replace `verify`, which can no longer pass. Every check below is **bound to the pair (patch SHA-256, candidate tree `T`)** recorded at the clean review. Run the gates in a fresh delivery-candidate worktree for that patch; its printed tree must equal `T` (if HEAD moved, or the patch changed, `T` differs: everything bound to the old `T` is void and the review is redone on the new candidate). Run each gate in a subshell, `(cd <dir> && export COMPOSE_PROJECT_NAME=bugfix-<bead>-<purpose> && pnpm install --frozen-lockfile && pnpm lint && pnpm check && pnpm test) > <log> 2>&1`, so the orchestrator's shell does not stay inside the worktree (fixpatch refuses every command except `check` when run from a bugfix worktree). After each gate finishes, `fixpatch.sh check <dir> <T>` must pass (a gate that rewrote a tracked file or left an untracked non-ignored one has validated a different tree). Record for each item below, on the bug bead (`--append-notes`): the patch SHA-256, the candidate tree `T` and its HEAD, the worktree path, the command, the process exit status, and the path and SHA-256 of the full current-run log (redirect the whole output to a file; a pasted tail is not evidence).

1. **Regression evidence (HIGH and MEDIUM; LOW where practical).** In the candidate's no-fix counterpart (`candidate <bead> none <dir>` for a HEAD + fix candidate, `materialize <bead> none <dir>` for a baseline + fix one: the original code the candidate is built on) add only the regression test (`git apply --include=<test path> <patch>`, or, for an in-source test (`import.meta.vitest`), a test-only patch the reviewer has checked carries no fix code) and run it: it must **fail for the expected reason**, the assertion or behaviour the bug describes. A type or import error, a missing fixture, an exception elsewhere or a timeout does not demonstrate the bug. Then run the same command in the candidate itself: it must pass. Same command, same fixtures, same environment.
   If an automated test is genuinely infeasible (behaviour only real devices show, such as an iPad or Chromebook wiping cookies or Safari seeking video differently from Playwright's WebKit; the school network; Caddy's access log on staging), record an explicit exception on the bead: why, with evidence, and the alternative reproduction (a scripted device session on the demo kit, a fixture replay, a captured staging log) showing the failure before and its absence after. The alternative reproduction must not capture pilot data: use the demo kit and seed data, and never record a real kit's events, codes, tokens or IPs. That alternative is reviewed by the reviewer like code. HIGH has no silent waiver.
2. **Gates.** The fast gate (`pnpm lint && pnpm check && pnpm test`) and the full gate (`pnpm e2e`; background, it takes minutes) from the root of the delivery-candidate worktree whose tree is `T`, with that worktree's own `COMPOSE_PROJECT_NAME` (see "The gates"), then `docker compose -p <name> down -v`. If the HEAD + fix candidate does not apply (unrelated work inside a hunk's context), ask Mike. A failure is a regression until shown otherwise; it is **pre-existing** only if the same command fails the same way on **the same base without the fix**: `candidate <bead> none` at the same HEAD for a HEAD + fix candidate (check both worktrees print the same HEAD and that the no-fix tree is `HEAD^{tree}`), `materialize <bead> none` for a baseline + fix one. Never compare a HEAD + fix gate against the dirty baseline: unrelated uncommitted work can make a HEAD failure vanish there, or add one HEAD does not have. Keep the two runs equivalent: fresh worktrees on the same filesystem, created the same way, the same command line from the same directory, the same fixtures and seed data (each run on a fresh database in its own Compose project), the same environment variables, run one after the other rather than concurrently; record both logs. A confirmed pre-existing failure gets its own linked bead and does not block closure **only if all hold**: the equivalent baseline run reproduces the same failure; the fix's relevant checks (its regression evidence and the tests covering the changed code) pass; and the independent reviewer, shown both logs, confirms the failure does not undermine validation of the fix. Report the result as "validated with a confirmed pre-existing gate failure" (naming it), never "all gates green". If attribution is uncertain, or the failure stops the gate before it validates the changed code, stop and ask Mike (Mike, 2026-10-23). A gate that stops before its own final status line (permission denied, missing tool, timeout) has not run. Never call a failure harmless from memory of a known quirk.
3. **Anything changing afterwards** (another correction, a rebase or new commit that changes `T` (then the head-moved route above, never `patch`), a file touched by hand in the user's tree or in the candidate) voids the review and every check bound to the old patch hash or tree: back to step 2. `verify` catches a changed fix in the user's tree, `check` a changed candidate worktree, and `staged` (Delivery) a candidate that no longer matches at commit time.

## Closure

A fix is complete when all hold, each with its record on the bead: the original invariant is restored; the regression evidence above exists (or the reviewed exception); the final patch's review has no related HIGH or MEDIUM finding open; every finding bead is closed with an independent resolution (reviewer-verified, reviewer-accepted rejection, or Mike's decision); unrelated defects are separate `discovered-from` beads, not children; `verify` passed (or, on a recorded head-moved route, `check` passed on the new candidate and `staged` at delivery); the clean review and both gates are recorded against the same patch hash and candidate tree `T`, and `check` passed after each; both gates passed there, or failed only with a confirmed pre-existing failure as defined in step 6.2, with exit status and log hashes recorded. Then close the bug bead.

## Delivery and commits

Report to Mike: root cause, the fix (patch hash and files), each finding and how it was resolved, any spun-off beads, the regression evidence and gate results. **Passing gates authorizes nothing by itself.** Commit only with Mike's explicit authorization (Mike, 2026-10-23; the conservative profile in AGENTS.md). One authorization can cover the whole session, so do not ask again for each fix within its scope. Mike's "commit per finished fix" preference sets the *granularity* (one commit per finished fix), not the permission. A "do not commit" in the current request wins. Never push, deploy, run Dolt remote sync or touch the live stack without separate authority. In JADE, merging or pushing to main deploys staging automatically (CLAUDE.md), so it needs that same separate authority as a deploy; a production deploy is always Mike's (CLAUDE.md "Stop and ask"). The commit message includes the bug's bead id (CLAUDE.md). When committing (the candidate is HEAD + fix, tree `T`):
1. `git diff --cached --quiet` must hold first. Anything already staged is someone's work: leave it staged, stop and ask Mike; never reset, restore or overwrite it.
2. Stage exactly the delivered patch: `git apply --cached <final.patch>`. It does not apply when an unrelated uncommitted edit lies inside one of its hunks, context lines included (tested: an edit three lines away blocks it, one further away does not); then stop and ask Mike how to separate them.
3. `fixpatch.sh staged <T>` must pass: the **whole staged tree** equals the reviewed and validated candidate tree. Matching file names are not enough (a different version of the same file, or HEAD having moved since `T` was built, gives the same names and a different tree). On a mismatch it prints the differing paths and changes nothing: stop and report to Mike. Do not unstage or reset to retry; if he agrees the staging was only yours, `git apply --cached -R <final.patch>` undoes exactly it. With this checkout's `core.filemode=true` an exec bit is already in the patch and in `T`, and nothing more is needed. Only on a `core.filemode=false` checkout, if the bead records `exec <path>` lines, set them now (`git update-index --chmod=+x <path>`) and run `fixpatch.sh staged <T> <path>...` again with exactly those paths: it then accepts only a 100644 → 100755 change with the same content on each listed path, nothing else.
4. Commit only under the existing explicit authorization, then run the same `fixpatch.sh staged <T> [<path>...]` once more (after the commit the index is HEAD's tree) and confirm `git diff --cached --quiet`.
Drop the baseline ref after the commit (`fixpatch.sh drop <bead>`) and remove the bead's worktrees with `fixpatch.sh cleanup <bead>`.

## Resume

After an interruption or compaction, before doing anything else:
1. `bd show <bead>` and `bd list --parent <bead> --all --json`: open findings, the last recorded patch hash, the recorded checks.
2. `git rev-parse refs/bugfix/<bead>^{tree}` must equal the recorded baseline tree (a missing note means the existing ref is the baseline; never re-baseline once edits began). If `git rev-parse HEAD` differs from `refs/bugfix/<bead>^`, do **not** run `patch`: follow step 6's head-moved route (or continue it, if the bead records one). Otherwise `fixpatch.sh patch <bead> <new path>` and compare its hash with the last recorded patch. Different means the tree changed since the last review: back to step 2 for that delta.
3. Check for unfinished validation: a gate with no recorded exit status was not run; a background gate's log without a final status line did not finish. Re-run, never assume.
4. Leftover worktrees: `fixpatch.sh cleanup <bead>` removes the bead's recorded ones that are idle and reports the rest (a refusal for "running process" means a gate may still be running: find it before going on). Worktrees it did not create are not yours to remove. A leftover that fixpatch was interrupted while creating (recorded but with no owner record, or present but unrecorded) is refused too: report it to Mike rather than removing it. Continue from the earliest unmet step. Notes and logs are evidence; the bead and finding states are the status.
